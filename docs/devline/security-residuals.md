# 開発ラインのセキュリティ残存リスク

fake PoC の Security レビューで見つかり、未対応または一部対応のものを記録する。H-1〜H-2 と M-1〜M-4 の対応は `adr-001-devline-foundation.md` を参照。
「状態」はこのブランチのコードで確かめた内容で、実走と本番の確認ではない。

## Medium

| ID  | リスク                                                                                                                                         | 状態                                                                                                                                                                                                                                                      | 対応する時期 |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------ |
| M-5 | 追記のみの制約を DB 所有者が迂回できる。制約は行トリガだけで、TRUNCATE、`DISABLE TRIGGER`、`DROP` を止めない。監査の連鎖は全行消去を検知しない | 未対応。所有者とアプリのロール分離、`BEFORE TRUNCATE` トリガ、連鎖の先頭ハッシュの外部保存が必要                                                                                                                                                          | 本番化の前   |

## 実 runner の堅牢化の後に残るもの

| ID   | リスク                                                                                                                                                                                                                                                                                                         | 状態                                                                                                                                                                                                                                                                                                                                                                                  |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R-1  | 差分の中身の検査は既知の値（そのまま・base64・hex・逆順・連結）と形だけを見る。暗号化や任意の符号化をした秘密は通る。追加の中身が公開されるのは private の Sandbox の PR まで                                                                                                                                  | 残す。Sandbox と作り物のデータに限る前提で受け入れる。キーは専用にして、漏れたら失効する                                                                                                                                                                                                                                                                                              |
| R-9  | 配備と一時確認のコンテナの外部通信                                                                                                                                                                                                                                                                             | 解消。`--internal` のネットワーク（`enable_icc=false`）で動かし、ポートを公開しない。host からコンテナの IP で確かめる（実 Docker の試験で外へ出られないことを確認）                                                                                                                                                                                                                  |
| R-10 | 動いている docker の命令と成果物の取得は SIGTERM で止めない（取得は最大 10 分、`docker load` は最大 10 分）。監視が先に強制終了すると、配備先を消した後で落ちた試行は取り直すまで環境が止まる                                                                                                                  | 一部対応。配備の工程は AI の工程の例外と別に受ける。SIGTERM の後は次を取らず、配備先に触る前の試行は pending へ戻す。lease は 120 秒で動いている間は 30 秒ごとに延ばすので、落ちた試行が塞ぐのは最大 120 秒で、次の起動で取り直す（上限 3 回。超えると版は不明）。DB に届かず延ばせない間に lease が切れると、別の worker が重ねて動きうる（1 台運用が前提。書き込みは fence で守る） | 常用の前           |
| R-11 | 再度の merge 承認で承認者が変わると最初の承認者のまま                                                                                                                                                                                                                                                          | 解消。押した人ごと・取消ごとに `release_approval` へ追記する                                                                                                                                                                                                                                                                                                                          |
| R-13 | 検査済みのイメージの所有は DB のイメージ ID と `msf-sandbox-verify:` のタグで判断する。イメージ自体に配備のラベルは付かない（付けると ID が変わる）。CI の GitHub ホストのランナーが改ざんされた場合はイメージ ID と tar の照合を通る。CI と host のイメージストアが違うと ID が一致せず止まる（安全側）       | 残す。実 GitHub の artifact では未確認                                                                                                                                                                                                                                                                                                                                                |
| R-14 | 確認済み（2026-11-01）: CI の `imageId` は manifest の digest で、host（overlay2）の ID とは値が違う。実物の artifact（Sandbox run 41274209884）で確かめた。`tarSha256` で固定した tar の config の digest を load 後の ID と照合する                                                                          | 対応済み                                                                                                                                                                                                                                                                                                                                                                              | -                  |
| R-12 | 戻した job を再び配備する経路はない。環境が空になった場合も新しい版で作り直す                                                                                                                                                                                                                                  | 仕様                                                                                                                                                                                                                                                                                                                                                                                  | -                  |
| R-7  | AI が書いた試験は API キーのあるコンテナで動く。`CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` で子プロセスからキーを除くが、実 CLI での効果は実走で未確認。効かなければ、または `/proc` 経由で読めれば、CLI を通さない API 呼び出しが予算の上限をすり抜ける。Anthropic Console の利用上限を併用する                     | 一部対応                                                                                                                                                                                                                                                                                                                                                                              | 実データの前に確認 |
| R-8  | AI のコードは外部通信を制限しない CI（GitHub ホストのランナー）でも動く。暗号化した秘密は検査を通り、人の確認の前に CI で実行される。AI のコンテナの秘密は API キーだけで、GitHub トークンは渡さない                                                                                                           | 未対応                                                                                                                                                                                                                                                                                                                                                                                | 実データの前に対応 |
| R-2  | worker がプロセスごと落ちると、push と記録の間の PR が開いたまま残る。試行の差しかえのときに古い PR を閉じられなかった場合（event `pr_superseded` の `closed:false`）も開いたまま残る。人がマーカーの job ID で閉じる                                                                                          | 残す。fence が切れた場合と、試行の差しかえ・古い版・停止は自動で閉じる                                                                                                                                                                                                                                                                                                                |
| R-3  | 落ちた worker の試行は、再取得まで計上されない。job を再開しなければ開いたままで、表示の費用が実費より少ない                                                                                                                                                                                                   | 残す。実費の上限は `--max-budget-usd` と Anthropic Console の利用上限で守る                                                                                                                                                                                                                                                                                                           |
| R-4  | 排他は DB ごとで、接続の喪失を検知するまでの間は 2 台目が動ける。状態の書き込みは fencing で守られるが、外部の PR は重なりうる                                                                                                                                                                                 | 残す。Sandbox の 1 台運用                                                                                                                                                                                                                                                                                                                                                             |
| R-5  | 照合の順序（`issue-adapter.ts` の `listIssuesSince`）: `since` は更新日時で絞るが `sort=created&direction=asc` で読むので、上限ページに達すると新しい Issue が読めない。読む間の更新で並びがずれると取りこぼしうる                                                                                             | 残す。上限に達したら `scanComplete=false` で再送しない（安全側）。取りこぼしの確認は fake GitHub のみ                                                                                                                                                                                                                                                                                 |
| R-6  | 削除済み Issue（`assertUpdateTarget`）: 更新先の Issue が管理者に削除されていると 404 で拒否し続け、その依頼の新しい版は投入できない。人が別の依頼にするか、記録を直す必要がある                                                                                                                               | 残す。誤った Issue へ送らない安全側の失敗。再作成の経路は未実装                                                                                                                                                                                                                                                                                                                       |
| R-15 | `ac-results` の生成元（`scripts/ac-report.mjs`）は head の checkout から CI で動く。AI の試験が実行中に書き換えれば、照合を通る偽の報告を作れる。中身のない試験に `AC-n:` と名付ける場合と同じく、AC の中身は人が確認する。job の AC の表示は依頼のいまの条件で判定するので、版の更新で古い job の表示が変わる | 残す                                                                                                                                                                                                                                                                                                                                                                                  | 実データの前       |
