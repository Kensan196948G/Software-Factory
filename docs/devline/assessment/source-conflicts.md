## SC-01: 品質ゲート付き自動マージ vs 人の承認を head SHA に結ぶ

**出典**

- 組織方針 `/etc/claude-code/CLAUDE.md` §5: 品質ゲートを満たす通常 PR は、追加の Y/N なしで自動マージしてよい。高リスク変更は Approval PR。
- 詳細仕様書 1-3、4-8、4-9、FR-39、BR-07、NFR-01/02、TC-N13: マージの承認は人だけが行い、承認は PR 先頭の SHA に結びつけ、新しいコミットで失効する。
- 利用者規則: AI による APPROVE を禁止し、AI レビューは必須承認と同等に扱わない。

**衝突の内容**: 組織方針の自動マージでは、対象 SHA に人の承認が記録されない。仕様をこの repo にも適用すると、自動マージと両立しない。一方、仕様がこの repo 自身の PR を対象にしているのか、開発ラインが作る製品の PR だけを対象にしているのかは、文書から一意に読めない。

**適用範囲（論点）**

| PR の種類                                     | 組織方針 §5        | 仕様 4-8 / 4-9 / FR-39          |
| --------------------------------------------- | ------------------ | ------------------------------- |
| この repo の通常 PR                           | 対象               | 不明（これが論点）              |
| この repo の工場定義の PR（CI、保護ルール等） | 対象の可能性あり   | FR-46 と 9-4 で管理責任者の承認 |
| 開発ラインが作る製品の PR                     | 製品の repo による | 対象                            |

**決定者**: repo 所有者。組織方針の例外や解釈が必要なら、組織方針の管理者も関わる。FR-46 の管理責任者が別にいるかは未確認。

**候補**

| 候補  | 内容                                                                                   | 影響                                                                                                                                                                                            |
| ----- | -------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 候補1 | この repo の PR は §5。SHA 承認は、開発ラインが作る製品の PR と FR-46 の変更に適用する | 今の PR は品質ゲートと保護ルールの適用後に進められる。工場定義の変更をどう切り分けるかの基準が必要。この repo で FR-39 の実地検証ができない                                                     |
| 候補2 | この repo も含め、全 PR に人の SHA 承認を求める                                        | 仕様に素直だが、§5 より厳しい運用になる。全 PR が人待ちになる。所有者 1 人の場合、GitHub では自分の PR を承認できないので、第 2 の承認者か、GitHub の外の承認記録（仕組みは未実装）が必要になる |

**決定までの扱い**: **merge を保留する。** 対象には未マージの PR #22〜#27 を含む。作業は commit と PR の更新までとする。

## SC-08: 版が上がったときの Issue の扱い

**出典**: 詳細仕様書 6-4（冪等キーは受付番号＋版）、IF-03（受付番号＋版で同じ Issue を更新）。実装（`request.issue_no` が 1 つ。2 回目以降は YAML を更新せず既存の番号を返す。`src/api/service.ts:1129-1136`）。

**決定者**: 仕様の管理者（DX 推進部）。Phase 1 の ADR に案を書き、承認を得る。

**候補**: (1) 同じ Issue を更新し、版ごとの記録は別に持つ。(2) 版ごとに新しい Issue を作り、前の Issue を閉じる。
