# Development-Dispatcher との接続仕様（未実装・未配備）

相手: `Kensan196948G/Development-Dispatcher`（別リポジトリ・Python・pre-merge で未配備）。2026-11-03 時点では**接続するコードを書かない**。この文書は「どちらが何を受けるか」「識別子」「失敗時の扱い」を先に決め、実装は相手の配備後に行うための整理である。

## 1. 前提

- 相手はまだ配備されていない。**HTTP 呼び出し・SDK・キュー連携をこのリポジトリに実装しない**（実装すると、動かない経路が本番の設定に混ざる）。
- 実装するときも、注文書・依頼者・承認者の実データは送らない。作り物だけで試験する。
- 認証は共有秘密（ヘッダ）または mTLS を想定する。トークンは URL・ログ・監査に残さない。
- 合否は CI（`ac-results` v2）だけを根拠にする。Dispatcher の自己申告を合格にしない（現行の `recordVerification` の不変条件と同じ）。

## 2. 役割分担（案）

| 項目                         | Software-Factory（このリポジトリ）                                                | Development-Dispatcher（相手）                                         |
| ---------------------------- | --------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 受付・承認・注文書           | **持つ**。受付番号、版、承認、注文書 YAML、`order_snapshot` の内容ハッシュを確定する | 持たない。受け取った注文書を実行の入力にする                           |
| job の状態と監査             | **持つ**。`queued`〜`pr_ready` と停止、`job_event`、`audit_log`                     | 持たない。実行の途中経過は自分のログに持ち、結果だけ返す               |
| 実行（実装・修正）           | 今は `docker-claude` が行う                                                       | pre-merge の実行を担当する想定（具体範囲は未確定）                     |
| 差分検査と push / PR 作成     | 今は host（worker）が行う                                                         | 行う場合は結果（head SHA・PR 番号・変更 path）を返す。合否は決めない   |
| CI の収集と合否               | **持つ**。`verification`・`ac-results` v2 を独立に読む                            | 持たない（CI の結果を自分の申告で置きかえない）                         |
| merge / 配備の判断            | **持つ**。人の承認、または明示設定された自動マージ（`DEVLINE_AUTO_MERGE`）        | 持たない。merge の口を呼ばない                                         |

## 3. 受け渡し（実装するときに決める形）

| 向き              | 何を                                                                                       | いつ                                                         |
| ----------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------ |
| SF → Dispatcher   | 依頼識別子、注文書（YAML）、対象 repo（`owner/name:repoId`）、base SHA、job ID、job の版     | job が `implementing` に入るとき（今はホストが AI を起動する） |
| Dispatcher → SF   | 実行結果（成功/失敗、head SHA、branch、changed paths、PR 番号、費用、ログ参照、失敗理由）   | 実行が終わったとき（または heartbeat）                        |
| SF → Dispatcher   | 取消・停止（job ID、理由）                                                                 | 人が取り消した・停止条件に達したとき                           |
| Dispatcher → SF   | 結果不明の照合に必要な情報（job ID、試行番号、作った branch / PR 番号）                     | 応答を失った後、SF が照合するとき                              |

- 冪等キーは **job ID + 試行番号（attemptNo）**。同じキーの再送は 1 回の実行として扱う。
- SF は Dispatcher の応答を信じて job を進めない。実行結果を受けた後も、差分検査・CI・AC の確認を SF 側で行う（現行の worker と同じ順序）。
- 実行中は heartbeat を受け、途絶えたら SF 側の lease / タイムアウトで止める。

## 4. 識別子

| 識別子             | 形 / 例                         | 発行元             | 用途                                                             |
| ------------------ | ------------------------------- | ------------------ | ---------------------------------------------------------------- |
| 受付番号           | `REQ-2026-0012`                 | Software-Factory   | 依頼・注文書・AC・PR ブランチ名の対応。Dispatcher は変更しない    |
| 注文書の版         | 整数（1, 2, …）                 | Software-Factory   | 版が上がったら古い job を無効にする                              |
| 注文書の内容ハッシュ | `content_sha256`（64桁 hex）  | Software-Factory   | `orderHash`。AC の v2 が依頼を指すときの識別子                    |
| job ID             | UUID                            | Software-Factory   | 実行の単位。冪等キーの一部。監査の対象                            |
| 試行番号           | 1 以上の整数                    | Software-Factory   | 同じ job のやり直しを区別する                                    |
| base SHA           | 40桁 hex                        | 対象 repo          | 実行の起点                                                       |
| head SHA           | 40桁 hex                        | 実行側             | PR の先頭。merge の承認・自動マージはこの SHA に結ぶ              |
| PR 番号            | 正の整数                        | 対象 repo          | 人が見る単位。PR 本文の先頭に job マーカーを置く                  |
| CI run ID / 試行   | 文字列 / 整数                   | GitHub Actions     | 合否と `ac-results` の取得元                                      |
| repoId             | 数値（例 `1440860477`）         | GitHub             | 名前の付け替え・譲渡の検出。`DEVLINE_TARGET_REPOS` と台帳に持つ   |
| merge の SHA       | 40桁 hex                        | 対象 repo          | merge 後の同一性確認と配備                                        |
| resource hash      | `content_sha256` と同じ値を使う | Software-Factory   | 成果物・注文書・AC の突き合わせ（新しいハッシュ体系は作らない）    |

## 5. 失敗時の扱い（案）

| 失敗                                   | SF 側の扱い                                                                                                  | Dispatcher への再送                   |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------ | ------------------------------------- |
| 接続できない / タイムアウト            | job は実行中のまま。lease・heartbeat の期限で止める。理由を `stop_detail` に残す                              | 同じ job ID + 試行番号で 1 回だけ照合 |
| 応答が 5xx / 本文が壊れている          | 結果不明。**盲目的に再送しない**。branch / PR / job ID で照合する（handoff の `unknown` と同じ方針）         | 照合で見つからなければ再送可          |
| 4xx（入力の誤り）                      | 実行を開始しない。`policy_violation` か設定エラーとして止める                                                 | 再送しない（入力を直す）              |
| 実行が失敗した（exit != 0）            | 0 円または申告額を計上し、`runner_failure` で止める（再開可）                                                | 再送しない（人が再開を判断）          |
| 差分検査に違反                         | merge しない。`policy_violation` で止める（再開不可）                                                        | 再送しない                            |
| CI の結果が揃わない / AC が未確認      | `ci_incomplete` で止める。CI を再実行してから人が再開する                                                     | 再送しない                            |
| 同じ job ID + 試行番号の二重実行       | 2つ目を実行しない（冪等）。先行の結果だけを採用する                                                          | 先行の結果を返す                      |
| SF が落ちて実行だけ残った              | 次の起動で lease を回収し、Dispatcher 側の実行を止める（取消 API を用意する）                                | 照合してから判断                      |

| 項目                               | 決める人 / 必要なこと                                                                     |
