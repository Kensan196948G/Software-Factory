1なぜ6フェーズで進めるのか

「小さく試して、確かめてから広げる」ための考え方です。

家を建てるとき、いきなり全部を建てる人はいません。まず地盤が持つかを調べ（PoC）、建てるかを決め（Go / No-Go）、模型で住み心地を確かめ（Prototype）、1部屋だけ住んでみて（MVP）、引っ越し前に本番そっくりの点検をして（Staging）、入居し（Release）、住みながら直していきます（運用・改善）。みらいSFも同じ順番で進めます。

1-1. 6つのフェーズと、それぞれの「問い」

各フェーズは、1つの問いに答えるためにあります。問いに「はい」と言える証拠がそろったら、ゲートで判定して次へ進みます。

1-2. 進め方の5つの約束

① 期間ではなく終了条件で進む

「3か月たったから次へ」ではなく、ゲートのチェック項目（GC）を満たしたら次へ進みます。BR-16 S1S7

② 判定は人が行い、記録する

ゲートの判定者・日時・結果・根拠を残します。判定はAIに任せません。BR-19

③ 小さく始めて広げる

最初は青信号の小さな道具、少ない部署とモデル現場1か所から。黄は担当者のチェック体制ができてから。赤は対象外のまま。BR-14 S3

④ 段階ごとに場所を分ける

試作・パイロット・本番前・本番で環境を分け、本物のデータは承認された範囲だけで使います。NFR-36

⑤ 道具の大きさで当てはめを変える

小さな改善は短い道のり、新しい黄信号の道具はPoCから。BR-20（12章）

1-3. 「動く」と「使える」と「任せられる」は別のもの

PoCで技術的に動いても、利用者が迷えば使われません（Prototype・MVPで確かめる）。少人数で使えても、人数が増えたり障害が起きたりしたときに安全とは限りません（Stagingで確かめる）。この3つを別々のフェーズで確かめることが、6フェーズの理由です。 S1

試作画面が動くことと、本番運用に耐えることは別の完了条件です。モック認証・仮データ・仮の権限制御が本番へ残らないよう、G2（MVP着手判定）で「試作から引き継ぐもの・作り直すもの」をはっきりさせます。 S1S7

32つの適用レベル

6フェーズは「工場そのもの」と「1つ1つの道具」の両方に使います。

A. 工場（みらいSF）そのもの

受付ステーション、注文書、AIの実装、検査機（CI）、PR、公開までのライン全体を、会社に導入する道のりです。1回だけ通ります（その後は運用・改善を回し続けます）。4〜10章はこのAを中心に書きます。

B. 1つ1つの道具（依頼）

ラインに流れてくる依頼（例：工事写真の圏外保存）が、道具として使えるようになるまでの道のりです。依頼の大きさと信号の色で、通るフェーズを変えます（T1〜T3）。詳しくは 12章。

Aは「工場を建てて動かし始めるまで」、Bは「工場で1つの製品を作って出荷するまで」です。工場ができあがったあとも、製品（道具）ごとに小さな6フェーズを回します。

3-2. どのフェーズにも共通の「やってはいけないこと」

  • 赤信号の仕事（人の命・安全、構造・品質の合否、お金の最後の決定、契約・法律の判断、人の処遇、会社としての発表）をAIに決めさせる道具を作ること。海の工事では「今日は船を出すか」「作業を止めるか」は船長・現場の責任者が決めます S4
  • 本物の図面・名簿・位置情報・写真の原本を、AIの作業場や検証環境へ持ち込むこと（NFR-04）
  • ゲートの判定を飛ばして次の環境へ配備すること（TC-P04）
  • 期間が来たことを理由に、終了条件を満たさないまま次へ進むこと（BR-16）

4PH1　PoC（技術検証）

中心の問い：技術的に成立するか？

「受付 → 注文書 → AIの実装 → 検査機 → 提出書類（PR）」の一本線が、安全に、証拠付きで動くかを、小さな見本1件で確かめます。
本番の工場を建てる前に、試作のラインで「1個だけ作ってみる」段階です。ここでは使いやすさや人数はまだ問いません。「この組み合わせで本当に作れるのか」「囲いの外に出ないか」を確かめます。

  1. 題材と問いを決めるFEAT-001（画面・API・権限・履歴を一通り含む練習台）か SITE-001（建設土木の見本。圏外保存）を選ぶ。両方行う場合は FEAT-001 から 提案

15用語

本書で使う言葉です。ほかの用語は 要件定義書 の用語集を見てください。

フェーズ
1つの問いに答えるための段階。PH1〜PH6
ゲート
フェーズとフェーズの間で、人が「次へ進んでよいか」を判定する関所。G0〜G5
終了条件
次へ進むために満たすべき条件。本書ではチェック項目（GC-xx）として書く
PoC
Proof of Concept。技術的に成立するかを小さく確かめること
Go / No-Go
先へ進む（Go）か、やめる（No-Go）かの判定。条件付きGo・やり直しもある
Prototype
利用者が理解・操作できるかを確かめるための試作。本番の仕組みではない
MVP
Minimum Viable Product。価値を確かめられる最小限の製品。限られた利用者に実際に使ってもらう
Staging
本番と同じ条件で、安全・安定を確かめる本番前の検証
Release
本番環境で、対象の利用者に正式に提供すること
段階的な公開
対象の部署・支店を順番に広げて公開すること
安定化期間
公開の直後、障害・問い合わせを毎日見守る期間
限定パイロット環境
MVP で使う、利用者を限った環境（オンプレミス想定）
テーラリング
依頼の大きさと色で、通るフェーズを変えること（T1〜T3）
モデル現場
新しい道具を最初に試してもらう現場。MVP では海の現場を推奨
現場の試し係
モデル現場で屋外・手袋・電波の弱い所などで実際に使い、「使える／使えない」を判断する人
公開承認
本番に公開してよいかの人の判断。マージ（完成版への取り込み）とは別のリスク判断
RTO／RPO
RTO＝止まってから戻すまでの時間の目標。RPO＝失ってよいデータの時間の幅の目標
P95
100回のうち95回はこの時間以内、という速さの目安
RACI
R＝実施する、A＝最終責任を持つ、C＝相談を受ける、I＝結果を知らされる
