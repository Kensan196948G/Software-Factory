2-8. SCR-06 状態変更（小窓）

前は、選べない状態も全部並んでいて「どれなら押せるの？」と迷いました。V1.0 では押せる状態だけを並べ、押せない状態は「なぜ押せないか・だれならできるか」を折りたたみで見られるようにしました。承認を選ぶと、承認前に見ておくべき点が自動で出ます。
部分仕様
上部「いま：（状態）（滞留 n日目）　操作する人：（名前）（役割）」

③ 候補よりゆるい色を選ぶと「候補（色）より ゆるい色 にします。理由をメモに書いてください。」を表示
④ 「赤」を選ぶと「赤信号の仕事はAIに決めさせません。道具の範囲が『材料集め・表示』までで、決定は人が行うことを確認しました」のチェック欄（必須）

編集時の記録更新日時を更新し、履歴に「内容を編集」

4-4. 実装の作業場（隔離環境）の仕様（FR-31、NFR-03）

4-9. マージ・公開・復旧・現場展開（FR-39〜42）

  1. マージ必須チェック合格・承認が有効・競合なしのときだけ、squash でまとめて main へ。main へは PR 経由でしか入らない
  2. ステージングへ自動配備成果物のハッシュが一致することを確認。DB変更は事前に検証
  3. ステージング検証本番と同じ条件で、権限・性能・復旧・外部連携・主要業務を確認。未確認が残れば公開しない
  4. 現場試用（現場向けのみ）モデル現場で、屋外・手袋・雨の日・海の上・電波の弱い所で使う。結果を受付の依頼のコメントとPRに記録
  5. 公開承認承認者が、マージとは別のリスク判断として公開を許可（G4）。成果物のハッシュに紐付け、リリースノートを付ける。対象者や機能を絞った段階公開も可
  6. デプロイデプロイジョブが、承認済みのハッシュの成果物だけを配備（作り直さない）。公開後30分（案）は重点監視
  7. 復旧（必要時）PR に書いた戻し方で戻す。アプリは直前の承認済み成果物へ30分以内、設定は15分以内（案）。DBは前向きの段階的な変更が基本で、目標は RTO 4時間・RPO 1時間（案、NFR-37）
公開してはいけないとき：未承認、ハッシュ不一致、受入条件の充足率100%未満、重大な不具合、復旧手順が未確認、凍結期間中。緊急の例外は管理者＋業務責任者の二重承認と事後の記録が必要です。
