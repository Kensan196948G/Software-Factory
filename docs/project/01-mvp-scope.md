# MVP Scope（2026-10-28）

## 1. 目的 → 利用者 → 課題 → 価値

| 項目 | 内容 |
|---|---|
| 目的 | 現場・部署の「困りごと」を、安全で検査可能な形で受け付け、承認済みの注文書として開発ラインへ渡せる状態にする |
| 対象利用者（MVP） | 個人利用者1名（DX推進部の担当者）。依頼者・受付担当・承認者の3役を兼ね、画面のロール切替で動作を確認する |
| 解決する課題 | 要望の入口がばらばらで、重複・滞留・優先順位が分からない（ISS-01）。仕様が口頭のままで合格の条件が検査できない（ISS-02） |
| 主要価値 | ①受付番号と状態で追跡できる ②信号の色と根拠が一目で分かる ③承認前に見落としを機械が点ける ④注文書YAMLで開発ラインへ渡せる |

## 2. 主要フロー（3本）

### F1 依頼を登録する（約10分）
ログイン → ホーム → 新しい依頼（7ステップ）→ カタログから道具を選ぶ → 困りごと・目的・利用者 → 道具の性質（信号候補と理由）→ 合格の条件（あいまい語の指摘と書き換え候補）→ 扱う情報・守ること → 確認して登録 → 受付番号採番（REQ-2026-xxxx）→ 下書き自動保存と再開。

### F2 承認する（受付担当→承認者）
ホームの「あなたの番」→ 内容確認中 → 承認待ち → 承認者が信号の色を最終決定 → 承認前チェック（△の確認・赤の確認・候補よりゆるい色の理由）→ 承認済み → 注文書YAML生成 → 開発ラインへ投入（MVPではIssue本文のコピーまで）。

### F3 進める・差し戻す・見る
ボード／一覧／詳細 → 状態変更（12状態・権限・遷移表で制御）→ 差戻し→再提出、見送り、取消 → 滞留の可視化（3日/7日）→ 検索・絞り込み → CSV/JSON出力 → カタログ参照。

## 4. 今回作る（In Scope）

- 認証（1ユーザー、scrypt、セッション、CSRF、レート制限）とサーバ側の役割判定
- 受付のCRUD、採番（年別・トランザクション）、状態遷移（12状態）、承認記録
- 信号候補（R1〜R6）、ものさし、合格の条件チェック、承認前チェック
- 注文書YAML、CSV（11列・BOM・CRLF）、JSON（{seq, items}）出力・取込
- 監査ログ（追記のみ・ハッシュ連鎖）、取消（論理削除）
- 下書き（サーバ保存・本人のみ）
- カタログ・部署マスタ（19部署・118件）と見本データ9件
- 空・読込・入力エラー・通信エラー・成功の各状態
- CI（型・Lint・テスト・ビルド・秘密スキャン・migration検証）
- Cloudflare Preview（Worker＋Tunnel）、Health Check、Runtime確認
- ドキュメント一式（要件対応表・DB・API・テスト・デプロイ・制限・復旧）

## 6. 受入条件（MVP）

1. 見本データでF1〜F3を最初から最後まで操作できる
2. 空・読込・入力エラー・通信エラー・成功を再現できる
3. 3日/7日の滞留が色以外（ラベル）でも分かる
4. キーボードだけで登録・承認・状態変更ができる
5. 不正な遷移・権限外の操作が 403/409 で拒否され、監査ログに残る
6. 空DBから migration → seed → 起動 → 主要Read/Write が再現できる
7. Preview URL で同じ操作ができる（UI/API/DB/Runtime）

## 7. 制約（MVPとして守る）

- 本番データ・個人情報・預かり図書を一切使わない（作り物データのみ）
- ローカルPostgreSQLをインターネットへ直接公開しない（Tunnel＋共有秘密）
- SecretsをRepository・ログ・画面・Memory・Seedへ保存しない
- 破壊的DB操作（DROP/TRUNCATE）は開発DBのみ・明示フラグ付き
- 既存仕様（画面ID・状態・エラーコード）を勝手に変えない。変える場合は理由を記録
