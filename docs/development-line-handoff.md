# 開発ラインに渡すもの（受付 → 開発ライン）

版: 1.0 / 2026-10-28
対象: 受付ステーションで承認された依頼を、開発ライン（AI実装・CI・PR）へ渡すときの**完全な仕様**です。

---

## 1. ひとことで

> 承認された依頼は、**「注文書YAML」＋「承認記録」＋「受付番号」** の3点セットで GitHub Issue になり、開発ラインはその Issue だけを見て実装を始めます。

```
受付（依頼） → 信号の色を決める → 承認 → 注文書YAML → GitHub Issue → 開発ライン
```

---

## 2. いつ渡すか

| 条件       | 内容                                                        |
| ---------- | ----------------------------------------------------------- |
| 状態       | `approved`（承認済み）以降                                  |
| 信号の決定 | `signal.decided` が入っている（承認者が決定）               |
| 注文書の版 | `order_version` ≥ 1                                         |
| 操作する人 | 受付担当 または 承認者                                      |
| 重複       | 同じ依頼で2回押しても Issue は増えない（`issue_no` で冪等） |

---

## 3. 渡すもの（全体像）

| #   | 渡すもの                   | 形式                              | どこに入る                 | 受け取る側の使い道           |
| --- | -------------------------- | --------------------------------- | -------------------------- | ---------------------------- |
| 1   | **注文書（作業指示書）**   | YAML                              | Issue 本文のコードブロック | 何を・誰に・どこまで作るか   |
| 2   | **承認記録**               | 文章＋Issue 本文のメタ            | Issue 本文                 | 誰が・いつ・何色で承認したか |
| 3   | **受付番号と版**           | `REQ-YYYY-NNNN` / `order_version` | Issue タイトル・本文       | 追跡と再承認の判定           |
| 4   | **合格の条件（AC）**       | YAML リスト                       | 注文書                     | テストと受入の基準           |
| 5   | **変更範囲・対象外・制約** | YAML                              | 注文書                     | 作りすぎ防止・禁止事項       |
| 6   | **必ず人に聞くこと**       | YAML リスト                       | 注文書                     | 作業を止めて確認する条件     |
| 7   | **受付へのリンク**         | URL                               | Issue 本文                 | 原本・履歴への戻り           |

> この7点で「開発ラインが判断できる材料」は揃います。添付ファイルの実体・個人情報・運用の見本データは渡しません（§8）。

---

## 4. 注文書 YAML の全項目

| 項目                          | 型           | 必須 | 内容                                                  | 元の受付項目     |
| ----------------------------- | ------------ | ---- | ----------------------------------------------------- | ---------------- |
| `schema_version`              | 文字列       | ○    | 形式の版（現在 `1.0`）                                | 固定             |
| `order_version`               | 整数         | ○    | 注文書の版。承認のたびに +1                           | 自動             |
| `id`                          | 文字列       | ○    | 受付番号 `REQ-YYYY-NNNN`                              | 受付番号         |
| `title`                       | 文字列       | ○    | 件名（60文字まで）                                    | 件名             |
| `kind`                        | 文字列       | ○    | 依頼区分（新しい道具／改善／不具合／相談）            | 依頼区分         |
| `department`                  | 文字列       | ○    | 部署名（19部署）                                      | 所属部署         |
| `catalog_tool`                | 文字列       | ○    | カタログの道具名。なければ「カタログ外」              | 道具             |
| `requested_by`                | 文字列       | ○    | 起票者                                                | 起票者           |
| `approver`                    | 文字列       | ○    | 承認者                                                | 承認者           |
| `status`                      | 文字列       | ○    | 承認時点の状態                                        | 状態             |
| `signal.suggested`            | 文字列       | ○    | 候補の色（青/黄/赤）                                  | 自動判定         |
| `signal.decided`              | 文字列       | ○    | 決定した色（未決定なら「未決定（承認者が決める）」）  | 承認者の決定     |
| `problem`                     | 文字列リスト | ○    | いま困っていること（1行ずつ）                         | 困りごと         |
| `purpose`                     | 文字列リスト | ○    | 目的（1行ずつ）                                       | 目的             |
| `users`                       | 文字列リスト | ○    | だれが使う（11区分）                                  | 使う人           |
| `places`                      | 文字列リスト | ○    | どこで使う（5区分）                                   | 場所             |
| `scope`                       | 文字列リスト | ○    | 作るもの（1行1項目）                                  | 作るもの         |
| `out_of_scope`                | 文字列リスト | ○    | 今回は作らない（空なら `[]`）                         | 作らないもの     |
| `acceptance_criteria`         | 文字列リスト | ○    | 合格の条件（1〜8件）                                  | 合格の条件       |
| `constraints`                 | 文字列リスト | ○    | 守ること（＋その他）                                  | 守ること         |
| `data_handling`               | 文字列リスト | ○    | 扱う情報（7区分）。なければ「特別な情報は扱いません」 | 扱う情報         |
| `parties`                     | 文字列       | ○    | 関わる相手（社内のみ／協力会社／発注者）              | 関わる相手       |
| `requires_human_approval`     | 文字列リスト | ○    | 必ず人に聞くこと（7区分）                             | 必ず人に聞くこと |
| `measure.people`              | 整数         | ○    | 使う人の人数                                          | 人数             |
| `measure.frequency`           | 文字列       | ○    | 頻度（毎日/毎週/毎月/ときどき）                       | 頻度             |
| `measure.minutes_per_time`    | 整数         | ○    | 1回あたりの手間（分）                                 | 手間             |
| `measure.est_hours_per_month` | 数値         | ○    | 月あたり削減見込み（参考値）                          | 自動計算         |
| `requested_at`                | 文字列       | ○    | 受付日時（JST、`YYYY/MM/DD HH:MM`）                   | 自動             |
| `wish_date`                   | 文字列       | ○    | 希望時期（空なら `""`）                               | 希望時期         |

### 4-1. 表記の約束（実装が迷わないため）

- 文字列はすべて**二重引用符**で囲む。改行は空白に置きかえる。
- 空のリストは `key: []`。
- リストは ` - "値"`（半角スペース1つ＋ハイフン）。
- `kind`・`department`・`parties`・`frequency` は**日本語の表示名**（コード値ではない）。
- `data_handling` は日本語ラベル（例：`"工事写真・検査記録の原本"`）。
- 金額・個人情報などは含めない（§8）。

## 5. GitHub Issue の実物（実測）

**タイトル**

```

```

**本文**（実際に作成された Issue #2 の全文）

````markdown

- 信号: 黄
- 部署: 支店工事部の現場（海の工事）
- 型: T3
- 受付: https://sf.mirai-dx-platform.com

### 注文書 YAML（承認時の版）

```yaml
````

### 5-1. Issue に付くメタ情報

| 行     | 内容                             | 出どころ     |
| ------ | -------------------------------- | ------------ |
| 承認者 | 承認した人の表示名               | 受付の承認者 |
| 信号   | 決定した色（青/黄/赤）           | 承認記録     |
| 部署   | 部署名                           | 受付         |
| 型     | T1/T2/T3（未設定なら「未設定」） | 承認時       |
| 受付   | 受付ステーションのURL            | 環境設定     |

> ラベルは付けません（リポジトリ側にラベルが無くても失敗しないため）。必要になったら追加します。

## 6. 承認記録（データベースに残るもの）

開発ラインは Issue から受付へ戻れば、次を確認できます。

| 項目           | 内容                             |
| -------------- | -------------------------------- |
| 承認者         | 表示名・利用者ID                 |
| 判断           | `approved` / `returned` / `held` |
| 決定した色     | 青・黄・赤                       |
| 候補の色       | 自動判定の結果                   |
| 承認前チェック | 6項目の点検結果（JSON）          |
| 注文書の版     | 承認した版番号                   |
| 日時           | 承認した時刻                     |

---

## 7. 履歴・監査（追記のみ）

| 記録     | 内容                                                                         |
| -------- | ---------------------------------------------------------------------------- |
| 受付履歴 | 受付・内容を編集・状態を「〜」に変更（操作者・役割・日時・メモ）             |
| コメント | 差戻し理由・相談・承認メモ                                                   |
| 監査ログ | 誰が・いつ・何を・結果（成功/拒否/エラー）・相関ID。ハッシュ連鎖で改ざん検知 |

---

## 8. 渡さないもの（重要）

| 渡さないもの                           | 理由                                           |
| -------------------------------------- | ---------------------------------------------- |
| 添付ファイルの実体                     | MVPはメタ情報のみ（保存先は未決 Q-17）         |
| 個人情報・健康情報・位置情報の実データ | 開発環境へ持ち込まない（NFR-04）               |
| 発注者から預かった図面・写真の原本     | 同上                                           |
| 金額・原価・契約の実データ             | 機密。必要ならダミー                           |
| 運用・DevOps・SecOps の見本データ      | 受付の注文書ではない（画面の見本）             |
| 社内コメントの全文                     | Issue には承認メモのみ。詳細は受付へ戻って確認 |
| 操作する人の個人メール                 | Issue には表示名のみ                           |

---

## 9. 渡し方（操作）

1. 受付ステーションで依頼を承認する（信号の色を決定）
2. 依頼の詳細 → 注文書タブで YAML を確認（コピー・ダウンロード可）
3. 「GitHub Issueを作成」を押す（受付担当または承認者）
4. Issue の URL が返る。依頼には `issue_no` が記録される
5. 2回目以降は「Issue #n 作成済み」となり、重複しない

API で行う場合:

```http
POST /api/requests/{id}/handoff
```

```json
{ "issueNo": 2, "issueUrl": "https://github.com/.../issues/2", "created": true }
```

## 10. 失敗したとき

| 状況                  | 動き                                  |
| --------------------- | ------------------------------------- |
| GitHub の設定がない   | 409 `ERR-405`（管理者に確認）         |
| GitHub に接続できない | 502 `ERR-304`。受付の状態は変わらない |
| すでに Issue がある   | 既存の番号を返す（作成しない）        |
| 承認前・取消・差戻し  | 409 `ERR-205`（注文書が無い）         |

再試行は安全です（`issue_no` により冪等）。失敗しても受付のデータは失われません。

## 11. 受け取った開発ラインが行うこと

| #   | 作業                                                       | 参照           |
| --- | ---------------------------------------------------------- | -------------- |
| 1   | 注文書の `scope` / `out_of_scope` の範囲で実装する         | 注文書         |
| 2   | `acceptance_criteria` をテストにする                       | 注文書         |
| 3   | `requires_human_approval` に触れる変更は**止めて人に確認** | 注文書         |
| 4   | 1ブランチ・1PR。PRには判断材料10項目をそろえる             | 要件定義書 7-1 |
| 5   | CI（ビルド・型・テスト・E2E・セキュリティ）を通す          | 詳細仕様書 4-5 |
| 6   | 承認は**対象コミット**に紐づける                           | FR-39          |
| 7   | 公開はマージとは別の承認（G4）                             | フェーズ計画書 |

## 12. 受入チェックリスト（渡す前）

- [ ] 信号の色が決まっている
- [ ] 合格の条件が1件以上・8件以下
- [ ] 「今回は作らない」が書かれている
- [ ] 扱う情報と、見られる人の範囲が書かれている
- [ ] 必ず人に聞くことが選ばれている
- [ ] 承認前チェックの △ を確認した
- [ ] 注文書の版が1以上
- [ ] Issue が1つだけ（重複なし）
