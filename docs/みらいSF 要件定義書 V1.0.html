1背景と、いまの困りごと

なぜこの仕組みが必要なのかを、現場・部署の声と、AI活用の注意点の両面から整理します。

1-1. 現場・部署で起きていること

受付ステーション試作（S5）に入っている依頼の見本から、社内の典型的な困りごとが見えてきます。海の上（作業船・台船）や電波の弱い現場、全国の支店ならではの困りごとが目立ちます。

部署いまの困りごと（依頼の見本）起きている問題
現場（海の工事）作業船や台船の上では電波が弱く写真が送れず、事務所に戻ってから整理し直している二度手間・残業
船舶事業部どの作業船が、いつ、どの港の現場にいるかを電話で確認しており、現場どうしの調整に時間がかかる確認の手間・調整ミス
安全KY活動記録の空欄や記入もれが、支店の安全パトロールのときに見つかる気づくのが遅い
経理部協力会社からの請求書を手で入力しており、月末に作業が集中する入力負荷・ミス
人事・労務時間外労働の上限に近づいていることに、月末まで気づけない法令リスク
営業本部国や港湾管理者などのサイトを毎日見て回っている定型作業の負荷
技術本部（設計・積算）作業船を使う工事の見積の作成に時間がかかる（「金額をAIで自動的に決めたい」という依頼も来る）赤信号の依頼が混ざる
購買部安全書類が出たかどうかを、電話とメールで確認している確認の手間
現場（海の工事）朝ごとに複数の予報サイトを見比べ、作業できそうな時間を手で書き出している段取りに時間がかかる

部署別道具カタログ（S4）では、こうした「あったら助かる道具」が19部署で118件洗い出されています（青52・黄47・赤19）。一方で、DX推進部の人手だけでは、これらを1つずつ作ることはできません。

1-2. 「AIに丸投げ」では解決しない理由

AIはプログラムを速く書けますが、まちがえることもあります。S1は次の点を明確にしています。

  • 生成されたプログラムの正しさや安全性は保証されない。だから独立したテストとレビューが必要
  • AIの「できました」という自己申告ではなく、検査（CI）の実行結果で合否を決める必要がある
  • 「動く」ことと「業務として正しい」ことは別。業務の正しさは使う部署の人が確かめる必要がある
  • 建設土木では、構造・仮設・安全など人命や品質に直結する判断をAIに決めさせてはいけない。海の工事では「船を出すか」「作業を止めるか」が代表（S3・S4）
現場で毎日おこる「面倒」は山ほどあるのに、作り手が足りない。AIを使えば速く作れるが、AIまかせは危ない。だから「AIが作る」「検査機が調べる」「人が決める」を役割分担した、安全な組み立てラインを社内につくる――というのがこのプロジェクトです。

1-3. 解決したい課題（ISS）

S7 が整理した10の課題です。本質は「作る能力」より「決める・確かめる・記録する能力」の不足です。いまの状態（As-Is）は実測していないため、PoC の中で調べます。

ID課題主な対応（V1.0の要件）
ISS-01要望の入口がばらばら（口頭・メール・チャット・Excel）で、重複・滞留・優先順位がわからない受付の一元化（FR-01、FR-08、FR-20、FR-52）
ISS-02仕様が口頭・暗黙知のまま。合格の条件が検査できない書き方注文書と合格の条件の標準化、書き方チェック（FR-05、FR-23、FR-54）

ISS-04生成AIの利用ルール・権限・証跡が整っていない隔離環境・権限境界・作業の記録（NFR-01〜NFR-05、NFR-12）
ISS-05検証が人まかせ（属人的）で、記録が残らないCIを独立した品質ゲートにする（FR-32、NFR-06、NFR-40）

ISS-10運用・改善が続かない運用で見つかったことを次の依頼に戻す（FR-43、FR-45、6フェーズの PH6）

2目的とゴール

何をもって「成功」とするかを決めます。

2-1. 目的

  • 現場・部署の困りごとを、早く・安全に「使える道具」にすること S1S3
  • 要望・仕様・実装・検証・承認・リリースを、1つの管理された工程（開発ライン）につなぐこと S1
  • AIの速さを活かしながら、品質・安全・統制（ルール）と、働く人・協力会社への配慮を守ること S1S4

2-2. 設計の軸

「自然言語で指示できるか」ではなく、「完了を機械的に判定できるか」を軸に設計する。 S1
たとえば「使いやすい申請画面」は検査機で判定できませんが、「申請者は自分の申請のみ閲覧でき、承認者だけが承認できる」は権限テストで判定できます。受付ステーション試作 V1.0 には、あいまいな言葉を検査できる書き方に言いかえる候補を出す機能（FR-54）を入れました。

2-3. 到達点（できあがったときの姿）

  • 依頼者が要望を登録すると、AIが仕様案・実装計画を作り、承認された範囲でクラウド上の実装・テスト・修正・PR（変更の提出書類）作成まで進める S1
  • 人は、業務要件の確定、信号の色の決定、重要な設計判断、最終マージ（完成版への取り込み）、本番公開を判断する S1
  • 現場向けの道具は、モデル現場（海の現場を推奨）で「現場で使える」と確かめてから、ほかの現場・支店へ広げる S3
  • すべての段階を「期間」ではなく「終了条件」で進め、PoC から運用・改善までの6フェーズを、ゲートの判定記録とともに追える S1S7

2-4. 評価の考え方

評価するのは、AIが何回動いたかやコードの量ではありません。

全社の評価軸 S1

「業務として受け入れられた変更を、どの品質・費用で届けたか」

建設土木の評価軸 S3

「現場の手間がどれだけ減り、安全と品質を守ったまま使えているか」

管理の単位 S1

「AIが何台動くか」ではなく「安全に統合できる変更が何件あるか」

具体的な指標は 13章 にまとめます。

5-5. 承認者の4つの責任

  1. 目的・対象・合格の条件を確定する「何を作るか」を決めるのは承認者です。受付試作 V1.0 では、承認のときに注意点（承認前チェック）が自動で出ます（FR-50）。
  2. 信号の色を決める赤はAIの役割を「材料集め・整理」に限ります。候補よりゆるい色にするときは理由を書きます。
  3. 業務として正しいかを判断する検査の合格は「不具合がない」ことの証明ではありません。業務の動きを確かめます。
  4. 残っているリスクを理解して承認する根拠・日時・対象（コミット・成果物）を記録します。承認したあとに中身が変わったら、承認を取り直します（BR-09）。

6-1. 信号の3色ルール

作る道具は、まず「どの色か」で仕分けます。色によって、任せ方と最後に決める人が変わります。海の上の現場でも、陸の現場でも、事務の仕事でも同じ信号を使います。 S3S4

青 どんどん任せる

記録・整理・検索・お知らせ。まちがえてもすぐ直せて、人やお金に直接ひびかないもの。
例：工事写真の整理、作業日報、作業船の予定表、書類の検索
決める人：現場の担当者＋DX推進部

黄 担当者のチェック付き

たたき台・比べっこ・見落としチェック。結果は必ず担当者・技術者が見て、採用するか決めます。
例：工程表のたたき台、KY記録の書きもれ確認、波・風の予報から「作業できそうな時間」の目安
決める人：担当の技術者（現場所長など）

赤 AIに決めさせない

人の命・構造・品質・お金・契約・人の処遇・対外発表の最後の判断。AIは材料集め・表示まで。
例：出航・海の作業を止めるかの判断、構造計算の合否、見積金額の決定
決める人：資格と責任を持つ技術者・責任者（船長を含む）

迷ったら1つ上の色（青か黄か迷ったら黄）として扱います。色の最終決定は、注文書を承認する人が行います。どの部署にも必ず赤の仕事があります。
海の工事の原則：天気・波・潮の予報を集めてわかりやすく見せるのはAIの得意なこと（黄）ですが、「今日は船を出すか」「作業を止めるか」は、船長や現場の責任者が決めます（赤）。
