## 0. 前提（名称の重複）

「F-2」は 2 つの文脈で使われている。本記録では、11-18 の画面予行（`docs/production/48`）の所見を **UI-F-2**、11-19 の開発ライン所見（赤の注文書の投入、#195 で修正）を **DL-F-2** と書く。UI-F-6 / UI-F-8 は画面予行の所見のまま。

## 1. UI-F-2（Medium）保持していない役割が「操作する人」に並ぶ — **修正済み**

- 旧: 利用者（`requester` のみ）でも「操作する人」に 3 役が並び、選ぶと画面だけ承認者として描画された（サーバは 403）。
- 現状: **#190/#192（main `b6779633`/`a7d9f55e`）で修正済み**。選択肢はセッションの利用者が持つ役割（`user_role`）だけになり、ラベルは「表示名（役割名）」。
- 根拠（コード）: `src/web/public/station.js` の選択肢生成が `holdsRole` で絞る。`POST /api/auth/role` は保持しない役割を 403 にする（サーバは不変）。
- 根拠（試験）: `tests/e2e/station-display-name.spec.ts` が「承認者の役割だけを持つ利用者: … 依頼者・受付担当は出ない」「依頼者の役割だけを持つ利用者: … 受付担当・承認者は出ない」を実サーバ・実 DB で検証。CI の e2e は `5700fa76` の main push（run `44422424052`）で success。

## 2. UI-F-6（Medium）画面の利用者名がログインアカウントではない — **修正済み**

- 旧: ダッシュボードや「操作する人」が Mirai-Info 名簿の見本社員名（「山田 敏久」等）で、ログインしたアカウントの表示名が出なかった。
- 現状: **#190 で修正済み**。表示名は `app_user.display_name` を正とし、名簿（`window.__SF_ACTORS__`）は起票者・部署の選択などの既存用途だけに残す。
- 根拠（試験）: `tests/e2e/station-display-name.spec.ts` が「こんにちは、<表示名>さん」・「操作する人」の表示名を確認し、名簿の代表者名（`山田 敏久` 等）が画面に出ないことを検証。CI の e2e は `5700fa76` で success。
- 残る制約: 承認依頼メールの本文は名簿名を使う場合がある（`MAIL_MODE=file` の送信簿で確認済み）。メール文面の是正は本項の対象外。

## 3. UI-F-8（Medium）サーバが拒否する遷移もダイアログに出る — **未修正**

- 再現: 承認者で依頼を開く → 「状態を変更」ダイアログ。`受付` から `承認待ち` など、サーバが拒否する遷移もラジオで選べる。
- 根拠（コード）: `src/web/public/station.js` の `canMove(role, from, to)` は `role==='approver'` のとき `from !== to` なら常に `true`。ダイアログの選択肢は `canMove` だけで作られる（`station.js` 1944 行付近）。サーバは `performTransition` で遷移を検証し、不正は 409 `ERR-201` を返す（層① A2 で実測）。
- 影響: 選べてしまう→送信→409 の赤トースト。状態・版は変わらず、認可の穴ではない。11-18 の業務受入では 5 回の拒否（監査 `request.transition_denied`）を生んだ。運用で「主ボタンの順に進む」を守れば回避できる。
- 修正案（実施する場合）: ダイアログの選択肢を、共有の `transitionOptions`（`src/shared/domain.ts`、allowed/reason/who を返す）から生成する。`station.js` の当該箇所の小変更＋ E2E（承認者で不正遷移が出ない）＋ 層①の再実行。サーバ規則と二重実装になるため、共有関数を正とする。
- 未修正のまま受容する場合の運用: 「状態を変更」は主ボタン（次に進む）を使い、ラジオで飛ばさない。拒否時はトーストの理由に従う。監査に denied が残ることは許容する。
