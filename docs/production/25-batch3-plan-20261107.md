## 2. 各項目の受入条件

### B3-01 C-07: 有効利用者 0 件の検知

- `GET /healthz` の `auth` に `usersActive`（**有効な `app_user` の件数だけ**）を追加する。メール・ID・名前は返さない。
- 取得できたときは数値。**DB は正常だが件数を取得できないときは `null`**。DB 不達のときはキーを省略する。
- `scripts/ops/healthcheck.mjs` は次で非 0 終了する: `usersActive === 0` / `null` / 整数以外・負数。
  **キーが無い場合だけ警告**（旧 API との版ずれ。監視の検査消失を緑にしないため、`null` は失敗）。
- 受入テスト（実在するファイル）:
  - `tests/unit/healthcheck-offsite.test.ts`（「healthcheck.mjs の認証状態（auth.status）」に 5 ケース追加）
  - `tests/integration/healthz-auth.test.ts`（無効な利用者を実在させ、`where is_active` の回帰を検出）
  - 変異テスト: `countActiveUsers` から `where is_active` を外すと integration が失敗すること
- 記録: `docs/api.md`（契約）、`docs/deployment.md`（監視項目 5）、`docs/limitations.md` C-07 を**一部解消**に更新。
- **リスク**: 参照は `select count(*) from app_user where is_active` のみ。個人情報を出さない。

### B3-03 L-03（第 1 段）: 添付の実保存

- 依頼（`request`）に対する添付のアップロード/ダウンロード。保存先は環境変数（既定 off）。
- 制限: 1 ファイル 10 MiB・合計 5 件・許可拡張子（pdf/png/jpg）・ファイル名は保存時に UUID 化（traversal 防止）・SHA-256 を記録。
- **migration は追加のみ**（`AGENTS.md` の additive 方針。`scripts/db.ts` の rollback は down を実行しない）。
  受入は「追加 migration の適用」＋`pnpm db:verify`＋「空 DB からの `migrate` 再構築」＋「既存 DB への適用」で取る。
  **down migration は作らない**（不可逆・破壊的操作を作らない。戻しは前方修正）。
- 受入: unit（上限・拡張子・traversal・SHA-256）、integration（認可・404・削除）、migration の適用と再構築。
- **範囲外**: ウイルス検査・原本の加工・クラウド保存。`docs/limitations.md` L-03 を「第 1 段のみ」に更新。

## 6. 進め方

- 実装は worktree を分離し、main チェックアウトは main/clean を保つ（autofollow の前提）。
- 各 PR は **pr-ready で exit 0 → CI 3/3 → 独立レビュー（Critical/High 0）→ squash マージ**。
- 1 項目 1 PR を原則とする。文書のみの項目（B3-07 / B3-09 / B3-06）は 1 PR にまとめてよい。
- 失敗・未実施・skip を完了と書かない。証跡は実測値・run ID・SHA で示す。
