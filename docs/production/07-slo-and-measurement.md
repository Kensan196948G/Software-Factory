# SLO と計測（Q-12 数値目標）

最終更新: 2026-11-04
対象: Staging（`127.0.0.1:8782` / `mirai-sf-*`）と本番（`127.0.0.1:8783` / `mirai-sf-prod-*`）
位置づけ: **本書は「実測」と「暫定案」である。決定ではない。** Q-12 の確定は、ここの数値を見て所有者が判断する。

## 1. なぜ計測するか

- Q-12（応答時間・可用性・RTO/RPO）は `docs/limitations.md` §4 と `AGENTS.md` §8 で**（案）のまま**。
- 一方で、RPO 1 時間だけは `docs/production/00-adr.md` §8-6 で決定済みで、`02-runbook.md` §5 の
  毎時バックアップがその実装。**決めた目標が守られているかを測る手段が無かった。**
- そこで、読み取りだけで測る道具（`scripts/ops/measure-slo.mjs`）を用意し、2026-11-04 に 1 回実測した。
  以後は同じコマンドで再計測でき、値を本書へ追記する。

## 2. 計測方法

```bash
# 応答時間・失敗率だけ（既定 2 URL × 30 回）
node scripts/ops/measure-slo.mjs

# SLO の証跡用（systemd / journal / backup manifest も集計。journal は直近 7 日）
node scripts/ops/measure-slo.mjs --count 30 --collect
# 同じもの（package.json のショートカット。引数はそのまま渡せる）
pnpm ops:slo --count 30 --collect

# 機械可読（stdout は JSON だけ。診断は stderr）
node scripts/ops/measure-slo.mjs --count 30 --collect --json
```

- 実装: `scripts/ops/measure-slo.mjs`（Node 22・依存追加なし。`node:` 組み込みだけ）。
- `/healthz` は `GET` のみ。`--count`（既定 30）回を `--interval-ms`（既定 200）間隔で叩く。
- 集計する項目: HTTP 状態、所要 ms、本文の `status` / `environment` / `db.ok` / `db.latencyMs` / `commit`。
- 百分位は **nearest-rank**（`ceil(p/100 × n) - 1` 番目）。**n=30 では p99 は最悪値と同じ**になる。
  応答時間の統計は**成功した応答だけ**から出す（失敗は失敗率で別に数える）。
- `--collect` の内容（すべて読取り）:
  - `systemctl --user show` … 主要 unit の `ActiveState` / `Result` / `ExecMainStatus` / 最終実行 /
    実行時間（`ExecMainStart*Monotonic` と `ExecMainExit*Monotonic` の差）/ `NRestarts`、timer の次回・最終
  - `journalctl --user -u <unit> --since "<days> days ago"` … healthcheck / backup / restore-drill /
    autofollow の成功・失敗の回数と最終時刻（**本文は出さず件数と時刻だけ**）
  - `~/.local/state/mirai-sf<env>/backups/*.manifest.tsv` … 件数、最新の鮮度、**間隔の最大値**、60 分超の回数、
    オフサイト送信記録（`*.r2.json`）の件数
  - `~/.local/state/mirai-sf<env>/healthcheck.json` … 連続失敗・累計失敗・最終失敗（監視の記録）
  - `~/.local/state/mirai-sf/autofollow.json` … Staging の main 追従の最終結果

### 2-1. 読取り専用の担保（本作業で守ったこと）

- サービス・unit・timer・DB・Cloudflare・設定ファイルに触れない。`systemctl` は `show` / `journalctl` は読取りだけ。
- `preview.conf` / `prod.conf` は読まない（秘密を含むため）。`/healthz` の本文は既知の項目だけを出す。
- 外部公開 URL（`sf.mirai-dx-platform.com` / `sf-prod.…`、Access 保護）は叩かない。対象は `127.0.0.1` の 2 本だけ。
- URL は `scheme://host:port/path` に落とす。資格情報付きの URL は引数として拒否する。パスは `~` に縮める。
- 副作用は「`/healthz` への GET が 30 回ぶんアクセスログに増える」ことだけ（アプリのログ行が増える）。

### 3-4. RPO（バックアップの鮮度と間隔）

`--collect` は `~/.local/state/mirai-sf<env>/backups` を読む。RPO の暫定目標は 60 分。

| ディレクトリ                         | manifest | dump  | オフサイト送信記録 | 最新 dump の鮮度                                       | 平均間隔 | **最大間隔** | 60 分超 | RPO 判定（鮮度）                                |
| ------------------------------------ | -------- | ----- | ------------------ | ------------------------------------------------------ | -------- | ------------ | ------- | ----------------------------------------------- |
| `mirai-sf-prod`（本番）              | 37 件    | 37 件 | 27 件              | **34.2 分前**（`mirai_sf_prod-20261104T060500Z.dump`） | 38.5 分  | **60.2 分**  | 4 回    | 満たす                                          |
| `mirai-sf`（Staging）                | 23 件    | 24 件 | 0 件               | 13.9 分前（`mirai_sf-20261104T062521Z.dump`）          | 242.1 分 | **727.4 分** | 14 回   | 満たす（ただし日次運用のため RPO 目標の対象外） |
| `mirai-sf-prodr`（参考・運用対象外） | 4 件     | 4 件  | 0 件               | 1492.2 分前（2026-11-03 14:47:04 JST）                 | 41.5 分  | 78.1 分      | 1 回    | 満たさない（古い検証用ディレクトリ）            |

- 本番は `mirai-sf-prod-backup.timer` が毎時 :05 に動き（`02-runbook.md` §5。ADR §8-6 の RPO 1 時間）、
  journal 内でも 4 回成功（最終 2026-11-04 15:05:14 JST、所要 14.8 秒）。
- **最大間隔 60.2 分**は、timer の発火精度による。旧 unit は `OnCalendar=*-*-* *:05:00` で
  `AccuracySec` を指定しておらず、systemd の既定は **1 分**（`systemctl --user show -p AccuracyUSec` で `1min`）。
  このため発火が :05:00 から最大 1 分ほど遅れ、開始時刻の差が 60 分を超える回が出た（実測の最大 60.2 分＝12 秒超過が 4 回）。
  → **2026-11-04 に unit を是正**した（PR #83）。固定時刻 + `AccuracySec=1s` でも実行時間の分だけ 60 分を超え得るため、
  `OnBootSec=2min` + `OnUnitActiveSec=55min` + `AccuracySec=1s` の「前回実行から 55 分」に変え、60 分に 5 分の余裕を持たせた。
  `Persistent` は `OnCalendar` 前提のため外した。停止・サスペンドで飛んだ場合は healthcheck の鮮度警告（既定 90 分）が検知する。
  監視は 90 分で余裕を見ている（`MIRAI_SF_HEALTH_BACKUP_MAX_AGE_MIN` の既定 90。`02-runbook.md` §7）。
  **是正後の最大間隔は次の計測で確認する**（本節の 60.2 分は是正前の実測）。
- Staging は日次（02:30）＋リリース前バックアップなので、間隔の最大 727.4 分は仕様どおり。
  **Staging に本番と同じ RPO を課さない**（課すなら timer を毎時に変える別の決定が要る）。
- `mirai-sf-prodr` は runbook に記載の無い古いディレクトリ（検証時のものと見られる）。合計に混ぜず、参考として出すだけにした。
- オフサイト（R2）: 本番の dump 37 件に対し送信記録 27 件。**記録が付くのは `mirai_sf_prod-20261103T081828Z.dump`
  （2026-11-03 17:18 JST）以降の世代**で、それ以前の 10 件は記録が無い（`02-runbook.md` §5 のオフサイト設定より前と見られる）。
  Staging は `MIRAI_SF_OFFSITE_CMD` 未設定のため 0 件。

### 3-5. RTO の材料（復元訓練の所要時間）

| unit                                        | 最終実行（JST）     | Result  | 所要時間（systemd の ExecMain 差分） |
| ------------------------------------------- | ------------------- | ------- | ------------------------------------ |
| `mirai-sf-prod-restore-drill.service`       | 2026-11-03 16:02:32 | success | **31.6 秒**                          |
| `mirai-sf-restore-drill.service`（Staging） | 2026-11-01 03:30:33 | success | **31.5 秒**                          |

- 訓練の中身（`scripts/ops/restore-drill.sh`）: 最新 dump を**一時DB**へ `pg_restore` → manifest との件数・
  監査ログ末尾ハッシュの照合 → `scripts/db.ts verify`（ハッシュ連鎖）→ 一時DB削除。
- 31.6 秒は「復元して検証が終わるまで」であって、**本番の受付を止めてから再開するまでの RTO ではない**

- 復元訓練の journal は保持期間の外で**記録が残っていない**（`mirai-sf-prod-restore-drill` は期間内 0 件）。
  上の所要時間は systemd の `ExecMain*Monotonic` から取った。

## 4. 暫定 SLO 案（決定ではない）

| 指標                  | 目標（案）                                     | 根拠にした実測（2026-11-04）                                                                 | 測定方法                                                                                      | 未達時にすること（案）                                                                     |
| --------------------- | ---------------------------------------------- | -------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `/healthz` の応答時間 | **p95 < 300 ms**（p99 < 500 ms も併記）        | p95 は Staging 5.0 ms・本番 3.3 ms（中央値 3.1 / 2.5 ms）。300 ms は実測の約 60〜90 倍の余裕 | `measure-slo.mjs --count 30`（127.0.0.1 直）                                                  | `systemctl --user status` と `journalctl --user` を見る。DB 起因なら `db.latencyMs` を確認 |

| RTO                   | **30 分**（案。復元訓練の実測から）            | 復元＋検証が 31.6 秒。切替・確認は未計測                                                     | `pnpm ops:prod:restore-drill` の所要時間（systemd の ExecMain 差分）                          | 訓練の失敗は `result` が `failed` になる。runbook §9                                       |
| `/healthz` の失敗率   | **0%**（30 回の試行で失敗なし）                | 両環境 30/30 成功、失敗率 0.0%                                                               | 同上                                                                                          | 1 回でも失敗したら `measure-slo.mjs` は終了コード 1                                        |

補足:

- 99.5%/月 は 30 日で **約 3.6 時間**の停止に相当する。5 分間隔の監視では 1 回の失敗が約 0.012 ポイント
  （8640 回/月のうち 1 回）に当たる。**99.5% を守るには失敗の通知が要るが、外部通知（Slack 等）は未実装**
  （`02-runbook.md` §7）。現状は `systemctl --user --failed` と journal を人が見るしかない。
- RTO 30 分の根拠は「復元 31.6 秒」＋「手順の余裕」であって、実測された全体 RTO ではない。§5 の訓練を
  1 回実施して置き換える。
- 応答時間の目標は**ローカル直叩き（127.0.0.1）**の値。Cloudflare Tunnel と Access を通した値は未測定（§5）。

## 6. 再計測と運用

```bash
# 1. 計測（読取りだけ。30 秒未満で終わる）
node scripts/ops/measure-slo.mjs --count 30 --collect

# 2. 証跡を残す（JSON は機械可読。stdout は JSON だけ）
node scripts/ops/measure-slo.mjs --count 30 --collect --json > ~/slo-$(date +%Y%m%dT%H%M%S).json

# 3. 結果を本書 §3 へ「日時つき」で追記する（値を丸めない。未測定は未測定と書く）
```

- 終了コード: `0`=計測できた（失敗率 0）/ `1`=計測失敗（引数不正・1 回でも失敗・1 度も成功しない）。
  監視や CI に載せる場合はこの終了コードを使う。
- 定期実行（timer 化）は**していない**。unit の追加は運用変更なので、承認後に別 PR で行う。
- 計測は 127.0.0.1 直叩きである。**Cloudflare Tunnel / Access / DNS を含む経路は含まない**（§5）。
- 数値は「その時点のスナップショット」。1 回の実行で傾向は分からないので、月間可用性と RTO は
  データをためてから確定する。

## 8. 既知の制約

- journal の保持が短い（§3-3）。**7 日・30 日の成功率は、このままでは測れない。** まず保持の延長が要る。
- n=30 では p99 は最悪値と同じ。p99 を目標にするなら標本数を増やす（`--count 200` など。所要は約 40 秒/URL）。
- `/healthz` は DB に `select 1` を 1 回投げるだけの軽い経路である（`src/api/db.ts` の `healthCheck`）。**アプリの重い画面や書込み API の応答時間を代表しない。**
- 本番の外形監視は 5 分間隔。5 分未満の停止は取りこぼす（可用性の評価はこの粒度になる）。
- 可用性の判定は「ローカルから見た `/healthz`」であり、利用者から見た可用性（Tunnel・Access・DNS・ブラウザ）ではない。
- 計測の副作用として `/healthz` のアクセスログが増える（30 回/URL）。それ以外の状態は変えない。
