## 2. 計測方法

```bash
# 応答時間・失敗率だけ（既定 2 URL × 30 回）
node scripts/ops/measure-slo.mjs

# SLO の証跡用（systemd / journal / backup manifest も集計。journal は直近 7 日）
node scripts/ops/measure-slo.mjs --count 30 --collect
# 同じもの（package.json のショートカット。引数はそのまま渡せる）
pnpm ops:slo --count 30 --collect

# 機械可読（stdout は JSON だけ。診断は stderr）
node scripts/ops/measure-slo.mjs --count 30 --collect --json
```

- 実装: `scripts/ops/measure-slo.mjs`（Node 22・依存追加なし。`node:` 組み込みだけ）。
- `/healthz` は `GET` のみ。`--count`（既定 30）回を `--interval-ms`（既定 200）間隔で叩く。
- 集計する項目: HTTP 状態、所要 ms、本文の `status` / `environment` / `db.ok` / `db.latencyMs` / `commit`。
- 百分位は **nearest-rank**（`ceil(p/100 × n) - 1` 番目）。**n=30 では p99 は最悪値と同じ**になる。
  応答時間の統計は**成功した応答だけ**から出す（失敗は失敗率で別に数える）。
- `--collect` の内容（すべて読取り）:
  - `systemctl --user show` … 主要 unit の `ActiveState` / `Result` / `ExecMainStatus` / 最終実行 /
    実行時間（`ExecMainStart*Monotonic` と `ExecMainExit*Monotonic` の差）/ `NRestarts`、timer の次回・最終
  - `journalctl --user -u <unit> --since "<days> days ago"` … healthcheck / backup / restore-drill /
    autofollow の成功・失敗の回数と最終時刻（**本文は出さず件数と時刻だけ**）
  - `~/.local/state/mirai-sf<env>/backups/*.manifest.tsv` … 件数、最新の鮮度、**間隔の最大値**、60 分超の回数、
    オフサイト送信記録（`*.r2.json`）の件数
  - `~/.local/state/mirai-sf<env>/healthcheck.json` … 連続失敗・累計失敗・最終失敗（監視の記録）
  - `~/.local/state/mirai-sf/autofollow.json` … Staging の main 追従の最終結果

### 2-1. 読取り専用の担保（本作業で守ったこと）

- サービス・unit・timer・DB・Cloudflare・設定ファイルに触れない。`systemctl` は `show` / `journalctl` は読取りだけ。
- `preview.conf` / `prod.conf` は読まない（秘密を含むため）。`/healthz` の本文は既知の項目だけを出す。
- 外部公開 URL（`sf.mirai-dx-platform.com` / `sf-prod.…`、Access 保護）は叩かない。対象は `127.0.0.1` の 2 本だけ。
- URL は `scheme://host:port/path` に落とす。資格情報付きの URL は引数として拒否する。パスは `~` に縮める。
- 副作用は「`/healthz` への GET が 30 回ぶんアクセスログに増える」ことだけ（アプリのログ行が増える）。

**この列は「計測時点の最新 dump が何分前か」だけを見る。RPO 1 時間の保証ではない。**
RPO は「最後に復元可能なスナップショット」がいつ作られたかで決まり、dump の完了、manifest の整合、
R2 送信の成否、実行遅延、失敗、ホスト停止を含む。したがって、間隔の設定やこの時点の鮮度だけから
「RPO を満たす／保証する」とは判定しない（本節末尾と §5 の未測定項目を参照）。

- 本番は `mirai-sf-prod-backup.timer` が毎時 :05 に動き（`02-runbook.md` §5。ADR §8-6 の RPO 1 時間）、
  journal 内でも 4 回成功（最終 2026-11-04 15:05:14 JST、所要 14.8 秒）。
- **最大間隔 60.2 分**は、timer の発火精度による。旧 unit は `OnCalendar=*-*-* *:05:00` で
  `AccuracySec` を指定しておらず、systemd の既定は **1 分**（`systemctl --user show -p AccuracyUSec` で `1min`）。
  このため発火が :05:00 から最大 1 分ほど遅れ、開始時刻の差が 60 分を超える回が出た（実測の最大 60.2 分＝12 秒超過が 4 回）。
  → **2026-11-04 に unit を是正**した（PR #83）。`OnBootSec=2min` + `OnUnitActiveSec=55min` + `AccuracySec=1s` の
  「前回の起動から約55分」に変え、目標60分に対して約5分の運用余裕を持たせた。ただし、この変更だけでRPO 1時間を保証するものではない。
  復元可能になる時点はdump・検証・R2送信の完了後であり、処理時間、実行遅延、失敗、ホスト停止も影響する。
  定時起動の間隔と、最後に復元可能なスナップショットの鮮度を区別して評価する。
  `Persistent` は `OnCalendar` 前提のため外した。停止・サスペンドで飛んだ場合は healthcheck の鮮度警告（既定 90 分）が検知する。
  監視は 90 分で余裕を見ている（`MIRAI_SF_HEALTH_BACKUP_MAX_AGE_MIN` の既定 90。`02-runbook.md` §7）。
  **是正後の最大間隔は次の計測で確認する**（本節の 60.2 分は是正前の実測）。
- Staging は日次（02:30）＋リリース前バックアップなので、間隔の最大 727.4 分は仕様どおり。
  **Staging に本番と同じ RPO を課さない**（課すなら timer を毎時に変える別の決定が要る）。
- `mirai-sf-prodr` は runbook に記載の無い古いディレクトリ（検証時のものと見られる）。合計に混ぜず、参考として出すだけにした。
- オフサイト（R2）: 本番の dump 37 件に対し送信記録 27 件。**記録が付くのは `mirai_sf_prod-20261103T081828Z.dump`
  （2026-11-03 17:18 JST）以降の世代**で、それ以前の 10 件は記録が無い（`02-runbook.md` §5 のオフサイト設定より前と見られる）。
  Staging は `MIRAI_SF_OFFSITE_CMD` 未設定のため 0 件。

#### 3-4-1. オフサイト送信記録の鮮度監視（2026-11-05 追加。検知範囲の拡大であって RPO の保証ではない）

従来の healthcheck は**最新のローカル dump の鮮度（90 分）だけ**を見ていた。R2 送信が失敗すると backup unit は
failed（終了コード 4）になるが、ローカルの dump は残るため、**dump が新しい限り healthcheck は OK のまま**だった
（`systemctl --user --failed` を人が見ない限り、R2 送信の停止が続いても気づけない）。

- `scripts/ops/healthcheck.mjs` に任意設定 `MIRAI_SF_HEALTH_OFFSITE_MAX_AGE_MIN` を追加した。設定時は
  `MIRAI_SF_HEALTH_BACKUP_DIR` 内の最新の `*.dump.r2.json`（`offsite-r2.mjs` が送信と読み戻し検証に成功した後に残す記録）の
  時刻が閾値より古い、または記録が 1 件も無いと **NG（exit 1）** にする。
- 「最新」は記録ファイル（lstat）の mtime が最も新しいもの。その記録の時刻は JSON の `uploadedAt` を使い、
  **正常に parse できた JSON オブジェクトに `uploadedAt` キーが無い場合だけ** mtime を使う。
- **fail-closed**: 次の場合は mtime へ逃がさず NG にする。
  - 最新記録が読めない・JSON として壊れている・JSON オブジェクトでない・サイズが 0 または 64KiB 超
  - `uploadedAt` が時刻として解釈できない
  - `uploadedAt` または mtime が現在より 5 分（時計ずれの許容幅）を超えて未来（負の経過分を正常扱いしない。許容幅内は 0 分として扱う）
  - 記録名（`*.dump.r2.json`）に一致するエントリが通常ファイルでない（シンボリックリンクは追跡しない）、または lstat できない
  - 保存先（`MIRAI_SF_HEALTH_BACKUP_DIR`）が無い・ディレクトリでない・読めない
- 閾値との比較は**ミリ秒**で行う（「90 分 + 1 秒」は NG）。分への丸めは表示だけ。
- ログには「何分前か」「どちらの時刻を基準にしたか」「記録のファイル名」と固定文言の NG 理由だけを出す。
  **記録の中身（バケット・キー・ハッシュ）と保存先のフルパスは出さない**（保存先は `MIRAI_SF_HEALTH_BACKUP_DIR` という固定表現で示す）。
- 既存の dump 鮮度確認（`MIRAI_SF_HEALTH_BACKUP_DIR`）も、保存先がディレクトリでない・読めない・dump の stat に失敗した場合に
  例外で落ちず（stack にパスが出ず）、固定文言の NG になるようにした。保存先が**無い**場合と鮮度の判定・メッセージは従来どおり
  （「保存先がありません」「dump がありません」の文言は保存先のパスを含む）。
- 不正な値（正の整数でない）や `MIRAI_SF_HEALTH_BACKUP_DIR` 未設定での指定は、設定ミスとして NG にする（値は出さない）。
- 未設定なら従来どおり確認しない（Staging は R2 送信を使わないので設定しない）。
- 本番 unit（リポジトリ内の `deploy/systemd/mirai-sf-prod-healthcheck.service`）に `MIRAI_SF_HEALTH_OFFSITE_MAX_AGE_MIN=90` を追加した。
  **実ユニット（`~/.config/systemd/user`）への反映は本 PR では行っていない**。反映は承認後に runbook の手順で行う。

限界（これで分かること・分からないこと）:

- これは**検知範囲の拡大**であり、RPO 1 時間を**保証するものではない**。90 分は「送信が 1 世代以上止まった」ことを
  5 分間隔の監視で拾うための閾値で、RPO の目標値（60 分）とは別物である。
- 見ているのは「ローカルの最新送信記録に書かれた `uploadedAt`（キーが無い記録では記録ファイルの mtime）」と、
  「最新のローカル dump に対応する記録の有無」である。
  `offsite-r2.mjs` は送信と読み戻し検証に成功した後にだけ記録を書くので、通常はこれが「最後に成功した時刻」に相当するが、
  healthcheck 自身は R2 を確認していない。R2 上の実体がその後に消えた・壊れた、
  バケットの権限が変わった、といった**送信後の変化は検知しない**（R2 からの復元訓練 `prod-offsite-drill` の範囲）。
- 送信記録はローカルのファイルなので、記録だけが残って R2 側に無い状態や、記録の手動作成・時刻改変は区別できない。
- dump と記録の世代の対応は、**最新世代だけ**を確認する（2026-11-07、PR #123）。最新のローカル dump に対応する
  `<dump名>.r2.json` が無い場合、dump の経過が猶予（`MIRAI_SF_HEALTH_OFFSITE_GENERATION_GRACE_MIN`、既定 10 分）
  以内なら送信中として OK、超えていれば NG にする。これにより「最新 dump の送信だけが失敗し、1 つ前の世代の記録が
  閾値内」の間の検知遅れは、猶予 10 分＋healthcheck 間隔 5 分に短縮された。一方、鮮度窓（90 分）内の
  **過去世代の記録欠落**や、healthcheck 停止中に世代が進んだ場合の取りこぼしは依然として検知しない。
- 最新 dump は mtime で選び、名前の規約（`<DB>-YYYYMMDDTHHMMSSZ.dump`）は検証しない。規約外の手動 dump を
  バックアップ保存先に置くと、それを最新世代として扱い、記録欠落で NG になり得る（本番の保存先に手動 dump を
  置かない運用）。`MIRAI_SF_HEALTH_OFFSITE_GENERATION_GRACE_MIN` は `MIRAI_SF_HEALTH_OFFSITE_MAX_AGE_MIN`
  より小さくする（大きくすると検知短縮効果が失われる）。
- 通知は未実装（§5）。NG は従来どおり `systemctl --user --failed` と journal に残るだけ。

### 3-7. RPO の実測レポート（`rpo-report.mjs`、2026-11-05 追加）

**これは残っているバックアップの実績から測った値であって、RPO 1 時間の保証ではない。**
§3-4 の「最新 dump の鮮度」と違い、期間内の**すべての間隔**と、**R2 送信成功記録**の間隔を見る。
R2 送信成功記録は「`offsite-r2.mjs` が送信と読み戻し検証に成功したときにローカルへ書く記録」で、
**R2 上の実体の存在・復元できるかは確認していない**（`prod-offsite-drill` の範囲）。

```bash
# 読取りだけ（バックアップ保存先と healthcheck の状態ファイルを読む。DB・R2・systemd には触れない）
pnpm ops:rpo-report --since 2026-11-03T09:00:00Z           # 表形式
node scripts/ops/rpo-report.mjs --since 2026-11-03T09:00:00Z --json   # 機械可読（stdout は JSON だけ）
```

- 対象: `--dir`（既定 `~/.local/state/mirai-sf-prod/backups`）の `<db>-YYYYMMDDTHHMMSSZ.dump`（同名の `.manifest.tsv` が
  通常ファイル・空でない・読めるものだけを完成した世代とする。時刻は dump の mtime）と `<dump>.r2.json`（時刻は `uploadedAt`）。
  healthcheck の状態ファイル（`--health-state`、既定 `~/.local/state/mirai-sf-prod/healthcheck.json`）の
  `totalFailures` / `consecutiveFailures` / `lastFailureAt` を補足として併記する（判定には使わない）。
- 出力（JSON のキー）: `local`（(a) ローカル dump の間隔）、`offsite`（(b) R2 送信成功記録の間隔）、
  `latestOffsiteRecorded`（(c) 期間の終わり時点で最新の「R2 送信成功記録あり」snapshot。実体・復元可否は未確認）、
  `healthcheck`（(d)）、`errors`（検証できないもの）、`verdict`（`ok` / `gap` / `insufficient` / `unverifiable`）。
- 期間: 既定は直近 7 日（`--days`）。`--since` でオフサイト設定前（2026-11-03 08:16Z 以前）などの対象外期間を除く。
  期間の開始をまたぐ間隔（開始前の最後の世代 → 期間内の最初の世代）は数える。開始前に世代が無い系列は、開始から最初の世代までを
  `leadingMinutes` として出すだけで判定に使わない。期間の終わり（`--until`、既定は実行時刻）時点の「最新からの経過」も閾値と比べる。
- 判定はミリ秒で比較する（60:00.000 は閾値内、60:00.001 以上は超過）。分への丸めは表示だけ（`60:00.097` のように
  分:秒.ミリ秒でも出す）。
- 終了コード: `0`=ローカル・R2 とも閾値超の間隔なし / `1`=あり / `2`=データ不足（判定に使える時刻が 2 つ未満）または検証不能 / `3`=引数不正。
  判定の優先順位は **検証不能 → 閾値超 → データ不足 → ok**。時刻が 1 点しかない系列でも、その時刻から期間の終わりまでが
  閾値を超えていれば閾値超（終了コード 1）とする（データ不足より優先）。検証できないものがあるときは、それが間隔を埋める
  可能性があるため閾値超とは断定せず終了コード 2 にする。
- 時刻は厳密に解析する（`--since` / `--until` / `uploadedAt` / healthcheck の時刻 / dump 名の時刻）。`Date.parse` は
  `2026-02-31` を 3 月 3 日に正規化して受理するため使わず、年月日時分秒とオフセット（±14:00 以内。14 時台は 14:00 ちょうどだけ）を範囲検証し、往復させて一致を確かめる。
  タイムゾーンの無い時刻も受け付けない。不正な引数は終了コード 3、不正な記録・名前は検証不能（2）。
- **fail-closed**: 次のものは黙って除外せず、「検証不能」として終了コード 2 にする。シンボリックリンク等の非通常ファイル
  （dump・送信記録・**manifest**。リンクは追跡しない）、lstat できないもの、空・読めない manifest、壊れた・読めない・64KiB 超・
  `uploadedAt` の無い／実在しない日時の送信記録、名前の snapshot 時刻が実在しない日時のもの、実行時刻より 5 分超未来の
  dump mtime / `uploadedAt`、dump 名の snapshot 時刻より 5 分超前の dump mtime / `uploadedAt`（世代と矛盾）、
  保存先が無い・ディレクトリでない・読めない。manifest が**無い** dump は完成した世代として数えない（件数だけ出す）。
- dump の中身は**ヘッダだけ**確かめる（0 バイトでない・読める・先頭 5 バイトが pg_dump -Fc のマジック `PGDMP`。満たさなければ検証不能）。
  読取り専用・軽量を保つため `pg_restore` は呼ばない。**この検査はヘッダの確認に限られ、dump 全体の完全性（途中の欠損・破損）は保証しない**
  （完全性は `restore-drill` の範囲）。
- 出さないもの: 送信記録の中身（bucket / key / sha256）、healthcheck の失敗理由の本文、例外の文言、不正な引数の値、
  **保存先・状態ファイルのパス**（`BACKUP_DIR` / `HEALTH_STATE` という固定表現と、既定か引数指定かだけを出す）。
- 構成: `scripts/ops/rpo-report.mjs`（入口）と `scripts/ops/lib/rpo/`（`args.mjs` 入力解析 / `scan.mjs` 読取り /
  `analyze.mjs` 集計・判定 / `output.mjs` 表形式 / `common.mjs` 定数・厳密な時刻解析）。

限界（これで分かること・分からないこと）:

- **実測であって RPO の保証ではない。** 残っているファイルの時刻だけを見る。
- **ホスト停止中・サスペンド中は計測できない**（バックアップも healthcheck も動かない）。停止の後に世代ができれば、
  その空白は間隔として現れるが、停止中に「その時点の RPO」を測ることはできない。
- 世代管理（`MIRAI_SF_BACKUP_RETENTION_DAYS`、既定 14 日）で消えた世代は数えられない。送信記録は backup.sh の世代管理の
  対象外のため、dump だけ消えて記録が残ることがある。
- R2 送信成功記録は「送信と読み戻し検証が成功したときにローカルに書く記録」である。**R2 上の実体の存在・整合・復元可否は見ない**
  （`prod-offsite-drill` の範囲）。記録の手動作成や時刻の改変も区別できない。
- dump の mtime を完成時刻として扱う。コピーや `touch` で mtime が変わると値が変わる（snapshot 時刻より 5 分超前の矛盾だけは検出する）。
- healthcheck の値は状態ファイルの累計で、期間を区切れない（§5 の月間可用性と同じ制約）。

## 8. 既知の制約

- journal の保持が短い（§3-3）。**7 日・30 日の成功率は、このままでは測れない。** まず保持の延長が要る。
- n=30 では p99 は最悪値と同じ。p99 を目標にするなら標本数を増やす（`--count 200` など。所要は約 40 秒/URL）。
- `/healthz` は DB に `select 1` を 1 回投げるだけの軽い経路である（`src/api/db.ts` の `healthCheck`）。**アプリの重い画面や書込み API の応答時間を代表しない。**
- 本番の外形監視は 5 分間隔。5 分未満の停止は取りこぼす（可用性の評価はこの粒度になる）。
- 可用性の判定は「ローカルから見た `/healthz`」であり、利用者から見た可用性（Tunnel・Access・DNS・ブラウザ）ではない。
- 計測の副作用として `/healthz` のアクセスログが増える（30 回/URL）。それ以外の状態は変えない。
- オフサイト（R2）送信の監視は送信記録の鮮度だけで、R2 上の実体の存在・整合は見ない（§3-4-1）。
