# R2 オフサイトバックアップの保持（ライフサイクル）計画

作成: 2026-11-05 JST。状態: **計画のみ。R2 の設定は未変更**（適用は所有者の数字選択と Y/N 後。ADR §8.2 Q4）。

前提は `02-runbook.md` §5 と `03-business-acceptance-and-operations.md` §5.1。

## 1. 現状

- 送信: `mirai-sf-prod-backup.timer`（55 分間隔）ごとに `scripts/ops/offsite-r2.mjs` が dump と manifest を非公開バケット `mirai-sf-prod-backups` のプレフィックス `mirai_sf_prod/` へ送り、読み戻して SHA-256 を照合する。
- 保持: アプリは R2 から削除しない。R2 側のライフサイクル規則は**未設定として記録中**。最新のクラウド設定は適用前に読取りで再取得する（未取得のまま断定しない）。
- ローカル: `MIRAI_SF_BACKUP_RETENTION_DAYS`（既定 14 日）。
- 現行の送信は**毎回 1 世代**で、日次・週次の区別（タグやプレフィックス）は無い。

## 2. 容量の基礎値

- 1 回あたり: dump 約 128〜137 KB（runbook §5 の概算と、2026-11-05 の事前バックアップ 137,422 bytes）+ manifest（数 KB）。以下は **1 回 140 KB、1 日 26 回（55 分間隔）≒ 3.6 MB/日**で概算する。データ増加は見込んでいない（増えれば比例して増える）。
- 料金（公式 2026-10-30 更新）: Standard storage $0.015 / GB-month、無料枠 10 GB-month/月。Class A 100 万/月・Class B 1,000 万/月が無料。削除は無料操作。出典: https://developers.cloudflare.com/r2/pricing/
- 1 回の送信で dump と manifest の 2 件を put（Class A）・get（Class B）するので、月 約 1,600 回ずつ。無料枠に収まる。

## 4. 適用方法（公式手順。Dashboard / Wrangler / API）

出典: https://developers.cloudflare.com/r2/buckets/object-lifecycles/ ・ https://developers.cloudflare.com/workers/wrangler/commands/r2/

- 権限: ライフサイクルの管理はバケット単位の操作で、API トークンなら `Workers R2 Storage Write` が要る。S3 アクセスキーは不要。wrangler は `wrangler login`（現行の OAuth）で使える。
- 読取り（適用前の取得）: `wrangler r2 bucket lifecycle list mirai-sf-prod-backups`
- 追加（案 B の例）: `wrangler r2 bucket lifecycle add mirai-sf-prod-backups <規則名> mirai_sf_prod/ --expire-days 90`
- `wrangler r2 bucket lifecycle set --file` は JSON で**構成全体を設定する**ため使わない（既存の規則を消すおそれ。公式はバケットに未完了マルチパートを 7 日で中止する既定規則があると説明している）。
- 規則は最大 1,000 件。プレフィックスを空にするとバケット全体が対象になるため、必ず `mirai_sf_prod/` を指定する。

## 5. 適用時の影響（既存オブジェクト）

- 公式: 規則を適用すると、**既存オブジェクトも新しい規則で期限が計算され**、期限を過ぎていればおおむね 24 時間以内（数が多いとそれ以上）に削除される。新規オブジェクトには即時に反映される。
- つまり、作成から 90 日を超えた dump は、適用後の短時間で消える。**規則を外しても消えた物は戻らない。**
- 2026-11-05 時点では、最古の送信は 2026-11-03（送信開始）なので 30 日案でも即時の削除は起きない見込み。ただし適用日で変わるため、適用直前に最古のキーの日付を確認する。

## 6. 適用前の退避と確認

1. `lifecycle list` で現行規則を取得し、JSON をローカル（0600）へ保存する（規則の内容は秘密ではないが、バケット名と合わせて社外へ出さない）。
2. `wrangler r2 object` で対象プレフィックスの最古のキーの日付を確認する。消える予定の世代があれば、所有者が残すと決めたものだけ別プレフィックス（規則の対象外、例 `hold/`）へ複製する。
3. 直前に `pnpm ops:prod:offsite-drill` で最新世代の取得・復元が通ることを確認する。
4. 適用後に `lifecycle list` で読み戻し、規則名・プレフィックス・日数を記録する。翌日に backup と offsite-drill を再実行する。
5. ロックとの併用: R2 のバケットロック（保持期間中は削除・上書き不可）は改ざん対策になるが、ライフサイクルと日数が矛盾しないよう別途判断する（今回は提案しない）。
