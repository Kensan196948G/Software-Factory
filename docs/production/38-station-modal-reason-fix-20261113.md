作成: 2026-11-13 JST。対象: Web UI（`src/web/public/station.js`）のみ。API・DB・認可・監査は変更しない。
状態: **PR #176 として提出（未マージ・未配備）**。マージと本番配備は所有者の判断待ちである。

実測はすべて隔離した検証用 DB（空の DB に migrate と seed を実行したもの）と、検証専用のポートで起動したサーバで行った。

## 2. 修正前の実測（main `5227b080`、2026-11-13 17:26〜17:41 JST）

### 2-1. パスワードの残存

操作: システム設定 → 利用者 →「利用者を追加」→ 表示名・メールアドレス・初期パスワードを入れて「追加する」。
成功のトーストが出てダイアログが閉じた後に、画面の中を調べた。

| 操作                                           | ダイアログ | `#modal` の入力欄の数 | パスワード欄の値             | `outerHTML` | localStorage / sessionStorage |
| ---------------------------------------------- | ---------- | --------------------- | ---------------------------- | ----------- | ----------------------------- |
| 利用者を追加して成功（`#uPass`）               | 閉じている | 7                     | **入力したパスワードのまま** | 無し        | 無し                          |
| パスワードを再設定して成功（`#uNewPw`）        | 閉じている | 1                     | **入力したパスワードのまま** | 無し        | 無し                          |
| 追加のダイアログを Escape で閉じる（`#uPass`） | 閉じている | 7                     | **入力したパスワードのまま** | 無し        | 無し                          |

- 残るのは入力欄の値（DOM のプロパティ）である。`value` 属性には書かれないため、`outerHTML` には現れない。
- 端末の保存領域（localStorage・sessionStorage）とトーストには出ていない。

### 2-2. 理由なしの状態変更

操作: 受付担当で、状態が「受付」の依頼の「状態を変更」を開き、メモを空のまま変更先を選んで「変更する」。

| 変更前 → 変更先   | サーバの決まり | 修正前の画面                                                                         |
| ----------------- | -------------- | ------------------------------------------------------------------------------------ |
| 受付 → 差戻し     | 理由が必須     | 送信前に止まる（「理由をメモに書いてください」）                                     |
| 受付 → 見送り     | 理由は任意     | 送信前に止まる（画面のほうが厳しい。変更しない）                                     |
| 受付 → 取消       | 理由が必須     | **成功のトースト「REQ-… を「取消」にしました」が出る**。その後にサーバの拒否が出る   |
| 現場試用 → 実装中 | 理由が必須     | **成功のトースト「REQ-… を「実装中」にしました」が出る**。その後にサーバの拒否が出る |

修正前の「取消」と「実装中への戻し」で、画面が出した表示と通信を順に記録した結果は次のとおりである。

| 順   | 取消（受付から）                                                   | 実装中への戻し（現場試用から）                                       |
| ---- | ------------------------------------------------------------------ | -------------------------------------------------------------------- |
| 1    | トースト（成功）「REQ-… を「取消」にしました」。ダイアログは閉じる | トースト（成功）「REQ-… を「実装中」にしました」。ダイアログは閉じる |
| 2    | `POST /api/requests/:id/transitions` → 400 ERR-102                 | `POST /api/requests/:id/transitions` → 400 ERR-102                   |
| 3    | トースト（失敗）「理由をメモに書いてください」                     | トースト（失敗）「理由をメモに書いてください」                       |
| 結果 | サーバの状態は「受付」のまま                                       | サーバの状態は「現場試用」のまま                                     |

回帰 E2E（§5）を修正前のコードで実行した結果は、失敗 3 件・未実行 3 件（直列の後続）・成功 3 件（exit 1）だった。

| 試験                                             | 修正前 | 失敗の内容                                                |
| ------------------------------------------------ | ------ | --------------------------------------------------------- |
| 利用者を追加した後、入力したパスワードが残らない | 失敗   | `#modal input, #modal textarea` が 0 件のはずが 7 件      |
| 理由なしの「取消」は成功の表示を出さない         | 失敗   | トースト `toast ok`「REQ-… を「取消」にしました」が出た   |
| 現場試用から実装中へ戻すときも理由が必須         | 失敗   | トースト `toast ok`「REQ-… を「実装中」にしました」が出た |
| 理由を書けば「取消」にできる                     | 成功   | —                                                         |
| 理由なしの「差戻し」「見送り」は送信前に止まる   | 成功   | —                                                         |

## 3. 原因

| #   | 場所                                | 原因                                                                                                             |
| --- | ----------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 1   | `closeModal()`                      | `#modal` から `open` を外すだけで、中身を消さない。次に `modal()` が中身を書き換えるまで入力欄が残る             |
| 1   | `ACT.uAddOk` / `ACT.uPwOk` の失敗時 | サーバが拒否してダイアログが開いたままのとき、パスワード欄に値が残る（旧画面は失敗時も空にしていた）             |
| 2   | `applyStatus()` の送信前チェック    | 理由が必須かの判定が `['back','hold']` だけで、サーバの `isReasonRequired()`（`src/shared/domain.ts`）と食い違う |

サーバが理由を必須にする遷移は、次の 6 組と「取消」への遷移すべてである（`REASON_REQUIRED` と `to === 'cancel'`）。

| 変更前                       | 変更先 | 修正前の画面が止めるか |
| ---------------------------- | ------ | ---------------------- |
| 受付・内容確認中・承認待ち   | 差戻し | 止める                 |
| 承認待ち                     | 見送り | 止める                 |
| 公開承認待ち・現場試用       | 実装中 | **止めない**           |
| （終了していない状態すべて） | 取消   | **止めない**           |

### 4-1. 設計の判断

| 論点                       | 採用                                                        | 理由                                                                                                                                                                                                                                                                    |
| -------------------------- | ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 閉じるときに何を消すか     | `#modal` の中身をすべて消す                                 | 成功・キャンセル・Escape・背景クリック・ログアウトは、すべて `closeModal()` を通る。パスワード欄だけを消す方法は、欄が増えるたびに漏れる。`index.html` の初期状態も空であり、開く前と同じに戻るだけである                                                               |
| ほかのダイアログへの影響   | なし（呼び出し 12 か所とボタン 7 個を確認）                 | 入力を読む処理（`applyStatus` / `dlReasonOk` / `vRiskSend` / `uAddOk` / `uPwOk`）は、すべて閉じる前に値を読む。承認完了ダイアログの進行（`lineModal`）は、要素が外れたら止まる作り（`isConnected` と `open` の確認）である                                              |
| 閉じる動き                 | 変更なし                                                    | `.modal` は `open` を外すと `display:none` になり、閉じるアニメーションは無い。中身を同時に消しても見た目は変わらない                                                                                                                                                   |
| 失敗して開いたままのとき   | パスワード欄だけ空にする                                    | 旧画面の挙動（`console.js` の `submitNewUser`「失敗しても残さない」）と、旧試験「403 は…パスワードを残さない」に合わせた                                                                                                                                                |
| 待つあいだに開き直したとき | 送信したダイアログの欄だけを空にする                        | 応答を待つあいだに閉じて別のダイアログを開ける。失敗の後で `#uPass` を探し直すと、新しいダイアログの入力を消してしまう（レビューの指摘。修正前の head で E2E が失敗することを確認）。旧画面と同じく、送信の前に欄の要素を覚えておく。`uPwOk` は最初から要素を覚えている |
| 「見送り」の理由           | これまでどおり常に必須                                      | サーバは承認待ち → 見送りだけを必須にするが、画面は以前から常に求めている。緩めると挙動が変わるため、変更しない                                                                                                                                                         |
| 判定の持ち方               | 画面に関数を 1 つ置き、単体試験でサーバの規則と突き合わせる | `station.js` は単体のスクリプトで、`domain.ts` を読み込めない。サーバの規則が増えたら単体試験が失敗する                                                                                                                                                                 |

### 4-2. 設計正本との差分

正本（`docs/design/software-factory-station-devsecops.html`）のメモの注記は「（差戻し・見送りは必須）」である。
正本には「取消」「公開承認待ち」の状態が無い（`docs/design/station-ui.md` §4-4 の許容偏差）。
この 2 つに伴う注記の追加は、同じ許容偏差の範囲として扱う。

## 7. 既知の制限

| #   | 内容                                                                                                                                                                                                                                                                                                                        |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | ダイアログが開いているあいだは、入力中のパスワードが入力欄にある（入力に必要なため）。入力の不足で止まったとき（表示名が空など）は、パスワード欄を消さない                                                                                                                                                                  |
| 2   | 保存の結果を待たずに成功の表示を出す作り（`applyStatus()` の保存以降、`submit()` など）は変更していない。理由の不足以外でサーバが拒否した場合（権限・版の競合など）は、これまでどおり成功の表示の後に失敗の表示が出る。別の変更で扱う                                                                                       |
