### 4.2 ケースS: 自己承認の拒否

1. §1のUI停止要因を解消してから開始する。Aが作り物の依頼Sを作成し、承認者に**A自身のID**を指定する。API補助方式を承認された場合は `POST /api/requests` に `approverUserId=AのID` を明示し、GETの結果で `applicantUserId=approverUserId=AのID` を確認する。名前一致や未紐付けで代用しない。
2. 入力例: 困りごと「架空の受付メモを一覧で確認したい」、目的「本番受入の確認」、対象「架空メモの整理」、対象外「実装・外部送信・実データ利用」。合格条件は「再読込後に依頼が1件表示される」等、確認可能な条件を設定する。
3. Aの受付担当ロールで `受付 → 内容確認中 → 承認待ち` に進める。
4. Aが承認者ロールへ切り替え、非同期更新の完了を待ち `GET /api/auth/me` で `actingRole=approver` を確認する。`GET /api/meta` で `environment=production`・`allowSelfApproval=false` も確認する。trueなら承認を試さず、設定差異として止める（本作業で設定を変更しない）。青信号・必要なチェックを確認して承認を試す。
5. 期待: サーバの HTTP 403 / `ERR-105`、状態は承認待ちのまま、`approval.self_denied` の監査が残る。
6. 別の認可エラー（例: 指名承認者が別人）ではERR-105の検証にならない。画面が操作を隠す場合は「UI抑止確認」と「サーバERR-105未確認」を分け、無理に成功扱いにしない。
7. Sは結果確認後に理由付き取消を行うか、所有者の判断で残す。取消前にも対象IDを照合し、物理削除しない。

### 4.3 ケースB: 別人承認から注文書

1. §1のUI停止要因を解消してから開始する。Aが別の作り物の依頼Bを作成し、承認者に登録済みBのIDを指定する。API補助方式を承認された場合は `POST /api/requests` に `approverUserId=BのID` を明示し、ケースSのIDと混同しない。
2. Aが `受付 → 内容確認中 → 承認待ち` まで進める。
3. 管理者による読み取り確認で、対象依頼の `applicantUserId` と `approverUserId` が別で、後者がBのIDに解決されていることを確認する。名前だけで未紐付けのまま進めない。
4. B本人が別ブラウザ/端末でAccess OTPログインする。`GET /api/auth/me` で本人IDと `actingRole=approver` を確認してから、対象ID・内容・対象外・合格条件を確認する。本人が承認を決める。
5. 青信号・承認前チェックを確認し承認する。期待: 承認済み、承認者がB、注文書versionが1以上、再読込しても状態が残る。

8. 注文書取得後で停止する。「Issueを作る（注文書を投入）」は押さない。受入対象は承認済みの確認記録として残し、廃止する場合は理由付き取消を所有者と確認する。

## 5. 運用残課題（対応案。設定は未変更）

### 5.1 R2保持期限

- 現在の手順書はR2保持を未設定と記録している。本作業ではCloudflare上の最新ライフサイクル設定そのものは未取得。
- **訂正**: ライフサイクル管理にS3キーは必須ではない。公式はDashboard、Wranglerログイン、Cloudflare APIを提供する。API権限は `Workers R2 Storage Write`。S3互換APIを使う方式だけ別のS3資格情報が必要になる。
- 推奨案（未承認）: `mirai-sf-prod-backups` の `mirai_sf_prod/` プレフィックスだけを90日で失効。ローカル14日は維持する。90日は監査行保持365日とは別のバックアップ保持案であり、復旧・法務要件を所有者が確認する。
- 実施順: 現行ルールを取得/退避 → 保持日数と対象の承認 → 既存ルールを壊さず追加 → 読み戻し → バックアップ送信とR2復元訓練の確認。
- **リスク**: 有効化後、既に期限を過ぎた物も削除対象となる。ルールを撤回しても消えた物は復活しない。バケット全体のルール置換やEmpty bucketは使わない。
- 資格情報: 現状のバックアップは所有者のWrangler OAuthに依存する。将来は対象バケット限定の専用資格情報と更新手順を検討する。保持設定のためだけに新しい秘密を増やさない。

公式: https://developers.cloudflare.com/r2/buckets/object-lifecycles/

### 5.2 監視と外部通知は分離して進める

- 現状の5分監視は **ローカルAPI** / DB正常 / commit / ローカルdump鮮度。外部のDNS・Access・Tunnel全体の到達性を保証しない。`REQUIRE_ORIGIN_SECRET` 有効時でもローカルhealth系は例外のため、ログイン後の通常画面が403でもhealthが正常になる場合がある。最初の認証後画面確認を省略しない。
- ローカルdumpが最新でもR2送信失敗は起こり得る。R2成功記録の鮮度と `mirai-sf-prod-backup.service` の失敗も監視対象にする案を推奨する。既存のdump鮮度監視だけでオフサイトRPOを満たすと判断しない。
- 通知先の承認後、既存のローカル監視失敗とバックアップ失敗に通知を追加できる。**通知送信そのものはAccessサービストークン待ちである必要はない**。通知先・保管方法・外部送信内容は別途承認が必要。
- 通知案: 連続失敗2回で初報、復旧時に1回、同一障害は30分間隔以上に抑制。バックアップ失敗は別系統で早期通知。数値は提案であり未実装・未承認。
- 通知に含めるのは環境名・失敗種別・時刻・安全な操作案内のみ。依頼本文・利用者メール・URL内トークン・資格情報・生レスポンスを送らない。
- 外部監視の第1段階: 公開URLの302とAccessの正しいログイン先を読み取り確認する（アプリ正常の保証ではない）。第2段階: 別ホストからAccess認証付き `/healthz` の200・JSON・environmentを検証する。公開health bypassは追加しない。
- **重要な権限上の制約**: 現行 `src/api/auth.ts` の `serviceTokenIdentity()` はサービストークンを `ACCESS_ALLOWED_EMAILS` の先頭、なければseed管理者メールへマッピングし、その利用者の権限を引き継ぐ（管理者代理となり得る）。Access tokenをアプリの `ACCESS_SERVICE_TOKEN_IDS` へ追加してUI E2Eを動かす案は広い権限を与えるため、そのまま本番監視用に採用しない。読み取り専用の機械ID/health専用設計を先に決める。外部healthだけでアプリ利用者セッションが必要かも経路を分けて確認する。
- 真に別ホストの監視が必要。同じホスト上のtimerだけでは電源・回線・ホスト全停止を通知できない。

公式: https://developers.cloudflare.com/cloudflare-one/access-controls/service-credentials/service-tokens/

### 5.3 利用者管理
