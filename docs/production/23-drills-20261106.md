## 1. 本番 R2 の欠落世代を再送（実施・2026-11-06 15:57 JST）

### 1-2. 実施

- 実行結果: `offsite-r2 OK bucket=mirai-sf-prod-backups … bytes=137767,457 sha256=30e0eb574049,22ab9dba998d marker=mirai_sf_prod-20261106T040035Z.dump.r2.json`（exit 0）。

- `pnpm ops:prod:offsite-status --count 4` が **OK / exit 0**。直近 4 世代すべてに `r2.json` があり、size と SHA-256 がローカルと一致する。
- 13:00 世代の `uploadedAt` は再送時刻（2026-11-06T06:57:53Z）になっている（元の実行時刻ではない）。**この点は記録として残す**。

## 2. Staging のロールバック訓練（実施・2026-11-06 15:58 JST）

本番配備の前に、実際の切替手順（release の current を別世代へ切り替えて再起動する）が動くことを Staging で確かめた。

| 手順 | コマンド | 結果 |
| ---- | -------- | ---- |
| 事前確認 | `bash scripts/ops/rollback.sh --dry-run a923352…` | exit 0（切替計画のみ） |
| 切り戻し | `bash scripts/ops/rollback.sh a923352…` | **1 秒**で完了。healthz の commit が `a923352` に一致、`status=ok`・`environment=staging`・`db.ok=true`・`auth.status=ready` |
| 切り戻し（戻し） | `bash scripts/ops/rollback.sh 199152e…` | **1 秒**で完了。healthz の commit が `199152e` に戻った |
| 影響 | — | 訓練中の 5xx は **0 件**。DB は戻していない（指示どおり） |

- 切替は `current` シンボリックリンクの差し替えと API の再起動で行われ、`healthz` の commit 一致で成功を判定している（試行 2 回目で一致）。
- **得られた知見**: 切替（`current` の差し替えと再起動）から `healthz` の commit 一致までが約 1 秒だった。これは**観測した経過時間**であり、コマンド単体の実行時間を計測したものではない（スクリプトに実行時間のログは無い）。本番では受付断が数秒発生する見込みで、`docs/production/02-runbook.md` §4 の受入チェックリストで確認する。
- 訓練後、Staging は元の世代（`199152e`）に戻した。main が進んでいれば自動追従が最新へ更新する。

## 3. N7（R2 保持）の実行準備（未実行）

- コマンド構文を実機で確認した（wrangler 4.154.0）:
  ```
  npx wrangler r2 bucket lifecycle add mirai-sf-prod-backups expire-90d mirai_sf_prod \
    --expire-days 90 --force
  ```
  - `add <bucket> <name> <prefix>` の位置引数と `--expire-days` を使う。
  - **`--force` を付けると確認プロンプトを飛ばす**。実行前に `list` で既存規則を確認する。
- 事前確認（2026-11-06 16:10 に実測）: `npx wrangler r2 bucket lifecycle list mirai-sf-prod-backups` の結果は **`Default Multipart Abort Rule`（7 日）のみ**で、期限・保持の規則は無い。
- 影響: **期限を超えた既存オブジェクトも削除対象**になる。過去の世代が消えるため、保持日数は所有者の選択（`docs/production/22` §7-2）が必要。
- 実施手順（承認後）:
  1. `list` で既存規則を記録する。
  2. 選択された日数で `add` を実行する。
  3. `list` で規則を読み戻し、`docs/production/13-r2-retention-plan.md` に記録する。
  4. 翌日のバックアップが成功し、`ops:prod:offsite-status` が OK のままであることを確認する。
