# 一覧の信号絞り込み（L-08）の性能実測

最終更新: 2026-11-04
対象: `GET /api/requests`（一覧）と起動データ（`GET /` の `items`）の取得
位置づけ: **本書は実測の記録である。** すべて合成データ（作り物）で測った。実データ・個人情報は使っていない。
測れていないことは §6 に「未測定」と書いた。

## 1. 何を変えたか

`docs/limitations.md` の L-08「一覧の信号絞り込みはサーバ取得後に JS で実施 → 数千件規模ではメモリを使う」を解消した。

|             | 変更前                                                                          | 変更後                                                                      |
| ----------- | ------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| 絞り込み    | 最大 5000 件を取得し、`(signalDecided ?? suggested)` を**全件** JS で計算・濾過 | `signal` を SQL の `WHERE`（`coalesce(signal_decided, <候補色の CASE>)`）へ |
| 件数(total) | 濾過後に残った件数（取得窓 5000 件の中だけ）                                    | 同じ `WHERE` で `count(*)`（取得窓の外も数える）                            |
| 画面        | 起動データを取得後に色で全件フィルタ                                            | サーバの絞り込み結果をそのまま描く（オフライン見本は従来どおり）            |
| ページ      | 最大 5000 件を取ってから JS で切る（5001 件目以降が空になる）                   | SQL の `LIMIT` / `OFFSET`（並びは `created_at` + `id` で安定）              |
| 索引        | —                                                                               | 0016: `request (created_at desc) where deleted = false`（追加のみ）         |

`signal` の判定は `src/shared/domain.ts` の `evaluateSignal` が正本である。SQL の CASE は
「引き上げのみ（下げない）」なので同じ最大値になる。等価性は結合試験
（`tests/integration/list-filter.test.ts`）で実際の PostgreSQL に対して全件突き合わせている。

## 2. 計測方法

- 実装: `scripts/perf/list-filter-bench.ts`（合成データの作成・計測・EXPLAIN をまとめた読み取り専用の道具。
  接続先は名前が `_test` で終わる DB だけを対象にする）。
- データ: `db/seed` の部署・道具カタログ（19 部署・118 件）＋合成の依頼。
  色の材料（`decides`・カタログの色・データ・社外・安全・承認者の決定）を決定的な式で散らしてある。
- 取得窓: 従来の実装と同じ `order by created_at desc limit 5000`。
- 反復: 各 21 回。暖機 3 回のあと、**変更前と変更後を交互に**測った。表は最小値と中央値。
- 変更前の経路では、色の候補の計算に JS の `evaluateSignal`（カタログの色は `catalog_tool.signal`）を使う。

## 3. 実測結果

「取得した行」は DB から受け取った行数、「残った行」は絞り込みの結果として残った行数
（API はこのあと `pageSize` で切る）。ms は**計測した関数の所要時間**（DB 往復・行の変換・JS の判定を含む）。

### 3-1. 10,000 件（色 = 青 / `signal=g`）

| 実装                                          | 取得した行 | 残った行 | total | 最小 (ms) | 中央値 (ms) |
| --------------------------------------------- | ---------: | -------: | ----: | --------: | ----------: |
| 変更前（0016 なし・取得後に JS で全件を濾過） |      5,000 |    1,484 | 1,484 |     179.5 |       192.1 |
| 変更後（0016 あり・SQL の WHERE）             |      2,965 |    2,965 | 2,965 |      98.5 |       103.8 |

- **メモリ**: 変更前は毎回 5,000 行（33 列）をアプリへ運び、全件の色を計算してから濾していた。
  変更後は該当する 2,965 行だけを受け取り、JS の全件判定をしない。返却行は 40.7% 減った。
- **件数の差（1,484 → 2,965）**: 変更前は「新しい 5,000 件の窓」の中だけで濾していたため、
  窓の外にあった青の依頼（差分の 1,481 件）が結果から落ちていた。変更後は `total` も`WHERE` で数えるので、
  同じ条件の依頼がすべて返る。**これは速度ではなく正しさの修正**である（5000 件を超えると
  変更前は静かに切り捨てていた）。
- 所要時間は 192.1ms → 103.8ms（中央値で 46% 減、88ms 短縮）。
- 同日 17:5x の別の実行でも中央値は変更前 183.5ms / 変更後 106.5ms で、同じ傾向だった。
  ホストは他の作業と同居しており、実行ごとに ±10ms 程度はぶれる。

### 3-2. 3,000 件（取得窓 5,000 件に収まる規模。同じ結果になることの確認）

| 実装                   | 取得した行 | 残った行 | total | 最小 (ms) | 中央値 (ms) |
| ---------------------- | ---------: | -------: | ----: | --------: | ----------: |
| 変更前（取得後に JS）  |      3,000 |      891 |   891 |      83.9 |       100.0 |
| 変更後（SQL の WHERE） |        891 |      891 |   891 |      32.0 |        38.7 |

- **残った行も total も 891 で一致した。** 変更前後で結果が変わらないことの実測。
- 所要時間は 100.0ms → 38.7ms（中央値で 61% 減）。全件を判定しないぶん、この規模でも差が出る。

### 3-3. 参考: サービス層全体（`listForActor`。要約の組み立てとページングを含む）

| データ量 | total | 1ページ | 最小 (ms) | 中央値 (ms) |
| -------: | ----: | ------: | --------: | ----------: |
|   10,000 | 2,965 |      50 |      27.6 |        30.0 |
|    3,000 |   891 |      50 |      12.2 |        14.5 |

変更前のサービス層は測っていない（旧実装の関数が残っていないため）。§3-1・§3-2 の差分は
「絞り込みの場所」の差であり、要約の組み立て（`yourTurn`・滞留日数など）は共通の処理である。
ここの数値は**ページ分（50 行）だけを要約する**実装（SQL の `LIMIT`/`OFFSET`）のもので、
以前の「5,000 件を取ってから切る」実装（同時刻の計測で 10,000 件・中央値 118.6ms）より軽い。

## 4. EXPLAIN ANALYZE

`EXPLAIN (ANALYZE, BUFFERS, COSTS OFF)` を、10,000 件のデータに対して実行した（`scripts/perf/list-filter-bench.ts explain`）。

### 4-1. 一覧の取得（`order by created_at desc limit 5000`）

| クエリ                             | 0016 なし                                      | 0016 あり                                                              |
| ---------------------------------- | ---------------------------------------------- | ---------------------------------------------------------------------- |
| 変更前の行取得（色の条件なし）     | 102.433ms（Sort: external merge, Disk 6928kB） | **48.499ms**（Index Scan using `request_list_created_idx`、Sort なし） |
| 変更前の件数（`count(*)`）         | 10.189ms（Seq Scan）                           | **3.081ms**（Index Only Scan）                                         |
| 変更後の行取得（色の条件あり・青） | 45.118ms（Seq Scan + quicksort 3082kB）        | 44.651ms（同じ計画）                                                   |
| 変更後の件数（色の条件あり）       | 13.700ms（Seq Scan + Filter）                  | 10.668ms（同じ計画）                                                   |

- 0016 は**絞り込み無しの一覧**（＝起動データ・ホーム・絞り込み前の一覧）に効く。
  10,000 行が work_mem に収まらずディスクへ溢れていた外部ソートが、索引の順読みに変わって消えた
  （102.4ms → 48.5ms）。
- 色で絞ったクエリは、候補色が `catalog_tool.signal` に依存するため式索引にできない。
  そのため 10,000 行では Seq Scan + 並べ替えのまま（45.1ms → 44.7ms は誤差）。
  **色の絞り込みの速さは 0016 ではなく「SQL へ移したこと」で出ている**（§3）。
- 0016 ありでの変更前の行取得が 48.5ms なのに、§3-1 の変更前の実測が 192.1ms なのは、
  §3-1 が「取得した 5,000 行の色を JS で全件計算して濾過する」ところまでを含むためである。

## 5. わかったこと

- 色の絞り込みを SQL へ移すと、10,000 件で中央値 192.1ms → 103.8ms（46% 減）、
  3,000 件で 100.0ms → 38.7ms（61% 減）。同じ条件で結果は一致する（3,000 件で確認）。
- いちばん大きいのは**アプリへ運ぶ行と JS の全件判定が減る**こと（5,000 → 2,965 行）。
- 0016 は色の絞り込みには効かないが、絞り込み無しの一覧の並べ替えを消す
  （102.4ms → 48.5ms、件数も 10.2ms → 3.1ms）。既定の一覧と起動データは常にこのクエリを通る。
- 10,000 件を超えると、変更前は 5,000 件の窓の外を**静かに落としていた**。
  変更後は `WHERE` と `count(*)` が同じ条件なので、返却件数と total が一致する。
- ページは SQL の `LIMIT` / `OFFSET` で取る。以前は 5,000 件まで取ってから JS で切っていたため、
  5,001 件目以降のページが空だった（`tests/integration/list-filter.test.ts` の 5,100 件の試験で確認）。
  同じ時刻の行があってもページの継ぎ目で重複・欠落しないよう、並びに `id` を足した（第1キーは変えない）。
- 画面の表は 1 回の表示で 5,000 件までしか出さない（`LIST_PAGE_MAX`）。`total` がそれを超えるときは、
  「全 N 件のうち、一覧に出せる上限（5,000 件）までを表示しています」と明示する（黙って切り捨てない）。

## 6. 未測定・残る制限

- **本番・Staging では測っていない。** 対象はローカルの合成 DB だけである（本番 DB へは書き込まない）。
- 同時接続・同時書き込みの下での性能は**未測定**（単一プロセス・単一接続で測った）。
- 10 万件以上での挙動は**未測定**。色で絞ったクエリは Seq Scan のままなので、
  行数に比例して遅くなる見込みだが、それは測っていない（推定）。
- ホストは他の作業と同居しており、load average は約 4.8 だった。中央値と最小値だけを載せ、
  ばらつきは §3-1 に書いた。同じコマンドで再計測できる。
- 画面側（`console.js`）は、色・状態・部署の絞り込みをサーバへ送る。**キーワード検索は画面側のまま**
  （API の `q` は起票者名を検索しないため、サーバへ移すと従来と結果が変わる）。
- 一覧の CSV / JSON 出力は、いま画面に出ている行をそのまま書き出す（従来どおり）。
- 画面の表はページ送りの UI を持たない（上限 5,000 件までを 1 回で出す）。ページ送りが要る規模になったら別途。
- 起動データが 5,000 件に達しているときは、絞り込み無しでも一覧をサーバから取り直し、`total` と上限表示を出す。
  ホームの `total` / 承認待ちは DB 全体で数えるが、**`yourTurn` / `stale3` は先頭 5,000 件の要約から数える**
  ため、5,001 件以上では過小になりうる（既知の制限）。
- ページ取得中に依頼が増減すると OFFSET の窓がずれる。重複を検出したら一度だけ先頭から取り直し、
  重複分は捨てるが、同時更新が続く場合の欠落までは防げない（一覧はスナップショットではない）。

## 7. 再現手順

```bash
# 1. 合成データを作る（接続先は名前が _test で終わる DB だけ。schema を作り直す）
node_modules/.bin/tsx scripts/perf/list-filter-bench.ts setup \
  --url 'postgresql:///mirai_sf_perf_test?host=/var/run/postgresql' --rows 10000

# 2. 変更前後を交互に 21 回ずつ測る（中央値・最小値・返却行数）
node_modules/.bin/tsx scripts/perf/list-filter-bench.ts measure \
  --url 'postgresql:///mirai_sf_perf_test?host=/var/run/postgresql' --signal g --iter 21

# 3. EXPLAIN ANALYZE（変更前の形・変更後の形・件数）
node_modules/.bin/tsx scripts/perf/list-filter-bench.ts explain \
  --url 'postgresql:///mirai_sf_perf_test?host=/var/run/postgresql' --signal g
```

- 0016 の効果を見るときは、`setup` のあとで
  `drop index request_list_created_idx;` を実行してから 2〜3 を測り、`db/migrations/0016_list_created_index.sql`
  を流し直して比べる（本書の §4-1 はその手順で測った）。
- `measure` は `src/api/repo.ts` の `listRequests` を直接呼ぶ（HTTP 層は共通なので含めていない）。
