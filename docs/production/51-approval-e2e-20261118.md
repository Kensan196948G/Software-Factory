## 6. 見つかった不具合

### F-1（Medium・修正済み）承認後の編集で `order_version` が二重に進む（A8）

- **再現**: 依頼作成 → 承認待ち → 承認（1 回目）。`order_version=1`。→ 管理者が内容を PATCH（`requestInputSchema` の全項目 + `version`）→ 200 / warning `ERR-202` / 状態 `wait`。このとき `order_version=2`。→ 画面から再承認 → `approved`、`order_version=3`。注文書タブも `order_version: 3`。
- **期待（依頼の A8）**: 編集では版を動かさず、再承認で `order_version=2`。
- **原因候補（コード読解）**: `src/api/service.ts` の `updateRequest` が `order_version = order_version + $30`（`$30 = afterApproval ? 1 : 0`）で編集時に +1 し、`performTransition` が承認時に `row.order_version + 1` でさらに +1 する。結果、承認済みの注文書の版が 1 → 3 と飛ぶ。
- **影響**: 注文書の版の追跡が「承認のたびに +1」と一致しない（`docs/development-line-handoff.md` の記載）。受付番号・内容・承認者との紐付けは正しく、データ破壊はない。層②でも修正前は同じ値だった。
- **修正**: PR #195（main `4d85c551`）。`updateRequest` の編集時の +1 を外し、`order_version` は承認時だけ +1 する。既存テストの期待も新仕様へ更新した。
- **修正後の実測**: 承認 1 → 編集後も 1 → 再承認で **2**、注文書タブも `order_version: 2`（A8 PASS、`--repeat-each=5` で 5/5）。証跡は `test-results/approval-iso-fix-repeat5/` と `approval-iso-fixed/`。
- **修正前の証跡**: `test-results/approval-iso-repeat5/evidence/*A8*.json`（`firstApproval.orderVersion=1` / `patch.orderVersion=2` / `reapproval.orderVersion=3` / `orderTab.header="order_version: 3"`）。

### F-2（Medium・修正済み）赤の注文書が開発ラインへ投入でき、Issue が作られる（B4 赤）

- **再現**: 一般利用者が `decides=r` で依頼作成 → 管理者が信号 赤・`redAcknowledged=true` で承認 → 承認者（または desk）が `POST /api/requests/:id/handoff`。**200 で偽 GitHub に Issue が 1 件作られる**。
- **期待（依頼の B4）**: 赤の注文書は投入できない（Issue を作らない）。
- **実測の補足**: 投入自体は成功するが、worker は `red_signal_human_required` で job を止める実装であり、AI の実装は走らない。ただし Issue は外部（GitHub）に残り、監査上も `handoff.succeeded` になる。
- **原因候補**: `handoffOrder` / `checkOrderForHandoff` に赤信号の判定が無い（`isRedOrder` は worker・配備・自動マージの側だけ）。
- **影響**: 赤信号の仕事が開発ラインの入口に載る。依頼の期待（投入不可）と実装が一致しない。層①の P1 は FAIL（修正前）。修正後は API が拒否し、層②③のスモークは開発ラインを使わない。
- **修正**: PR #195（main `4d85c551`）。API の境界（旧ルート・新ルート）で `refuseRedHandoff` を呼び、409 `ERR-205`・監査 `handoff.intent` denied（`why=red_signal`）・Issue/job を作らない。修正前に投入済みの赤 job に対する worker の `red_signal_human_required` は多層防御として残した。
- **修正後の実測**: 赤の handoff が 409 `ERR-205`、Issue 0 件、job 0 件、監査 denied（B4 赤 PASS、`--repeat-each=5` で 5/5）。証跡は `test-results/approval-iso-fix-repeat5/`。
- **修正前の証跡**: `test-results/approval-iso-repeat5/evidence/*B4*赤*.json`（`handoff` 200、Issue 番号、本文）。

### F-3（Low）403 の再送で拒否要求と監査が二重になる（A7・既知の再送の副作用）

- **再現**: A7 で自己承認を試みると、`POST /api/requests/:id/transitions` が **1 操作で 2 回**送られ、どちらも 403（監査の denied も重複し得る）。画面の `station-bridge.js` は 403 のとき CSRF を取り直して 1 回再送する実装のため、権限拒否でも再送される。
- **影響**: 状態・版・信号は不変で、認可の穴ではない。監査と通信が余分に増える。doc48 F-7（役割切替の重複）と同種。
- **証跡**: `test-results/approval-iso-repeat5/evidence/*A7*.json` の `http4xx` に 403 `/transitions` ×2。

### 既知の穴 C1/C2（修正して解消・2026-11-19）

- **C1（修正前）**: `DEVLINE_AUTO_MERGE=1` の判定（`decideAutoMerge`）は注文書の信号を見ておらず、条件を満たせば**黄の注文書でも自動マージの対象**になった（赤は `isRedOrder` で除外）。`test.fail()` で記録。
