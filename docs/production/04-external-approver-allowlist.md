## 2. Cloudflareで同じ1件を個別許可（所有者の操作）

1. [Cloudflare管理画面](https://dash.cloudflare.com/) → Zero Trust → Access controls → Applications。
2. 本番の「Mirai Software Factory 受付ステーション（本番）」を開き、ホスト名が **sf-prod.mirai-dx-platform.com** であることを確認する。
3. Policiesから上記専用Allowポリシーを開く。既存のInclude / Require / Excludeをローカルの安全な場所へ控える。画面写真にはメールが含まれるためチャットに貼らない。
4. **Include → Emails** に追加する方の実メール1件を入力する。既存の会社ドメインと個別メールを残す。
5. Action=Allowを維持。Everyone、Emails ending in=gmail.com等、Bypass、Service Auth、Temporary authentication等は追加しない。
6. 保存し、再度開いて「以前の条件＋その1件」だけであること、他アプリとの共有ポリシーに変わっていないことを確認する。アプリ側にも保存が必要なUIなら保存する。
7. この操作で本人へOTPを要求しない。ログインを試すまでは認証コード送信を行わない。

公式: https://developers.cloudflare.com/cloudflare-one/access-controls/policies/policy-management/

## 3. Linux端末でアプリ側へ同じ1件を追加

本番ホストの設定所有者ユーザーとして実行する。sudo不要。メールを引数や環境変数に書かない。

```bash
cd /mnt/storage/Software-Factory/Software-Factory
node_modules/.bin/tsx scripts/ops/allow-email.ts --check
```

事前確認OKを確認後:

```bash
node_modules/.bin/tsx scripts/ops/allow-email.ts
```

入力:

1. 実メールを2回入力（Cloudflareに追加したものと同じ）。
2. 表示されたメールと本番ホストを確認する。
3. Cloudflareの保存・読み戻しが終わっている場合だけ `CF-SAVED`。
4. 同時に設定編集・配備・ロールバックを行わない保守時間を確保した場合だけ `MAINTENANCE`。
5. 本番APIの短時間の再起動を実施してよい場合だけ `APPLY`。

各確認は指定文字以外（空欄を含む）なら説明付きで再質問し、3回不一致で変更なし中止する。明示的な `CANCEL` でも変更なし中止する。`kensan@…$` はシェルへ戻った表示なので、そこへ確認文字だけを入力しても続きにはならない。

`APPLY`までのCtrl+Cは中止。反映開始後は完了/復旧結果を待つ。メールは端末に見えるが、シェル履歴へは渡さない。端末録画やスクロールバックは各自で管理する。

### コマンドの安全条件

- 固定の本番設定だけを読む。所有者・通常ファイル・0600以下・シンボリックリンク/ハードリンクなしを検査。親ディレクトリは同じ所有者で他人の書込み不可。
- 設定の重複キー・未対応形式は停止。NODE_ENV/APP_ENV=production、Access JWT設定、ALLOW_SELF_APPROVAL=0、MAIL_MODE=offが必要。
- 稼働unitのWorkingDirectory・PID・実プロセスの非公開環境を確認し、許可設定/JWT/環境/メール/自己承認が設定ファイルと一致することを検査。秘密値は出力しない。
- 前後でローカルhealthのproduction/DB正常/commit一致と、実プロセスの設定一致を検証する。これは本人のAccessログイン成功を意味しない。反映後は既存管理者がブラウザを再読込してコンソールを確認する。新規承認者のログインは利用者登録が済むまで403になり得るため、認証を弱めて対処しない。
- 個別メールリストの先頭はサービストークンの既存identityにも使われる。先頭/既存順序を維持して末尾追加し、空リスト＋有効サービストークンがある場合はidentityが変わるため停止する。
- `ACCESS_ALLOWED_EMAILS` だけを追加し、既存許可を保持する。メールが既に許可されていれば再起動しない。
- 退避先は設定ディレクトリ内 `allow-email-backups/`（0700）、退避ファイル0600。元設定と候補には秘密が含まれるため、リポジトリ・チャットへ持ち込まない。
- 設定更新・再起動の排他と復旧記録を使う。反映直前に元ファイルとのバイト比較を行い、不一致なら停止する。比較とrenameはOSの原子的CASではなく、異なるツールでの同時編集を完全には排除できない。**実行中は手動設定編集・配備・ロールバックを行わない保守時間を確保する**。同時作業の不在を確認できない場合は適用しない。
- 再起動対象は `mirai-sf-prod-api.service` だけ。DB変更・利用者作成・通知送信・Cloudflare操作はしない。

## 4. 失敗時の扱い

- 反映前のエラー: 変更しない。原因コードを伝える。実メール/設定本文は送らない。
- 反映後の確認失敗: 元の設定へ復旧し、同じunitを再起動して健康状態を再確認する。他の操作で設定が変わっていれば上書き復旧せず停止する。
- 自動復旧を確認できない場合: 表示された退避ファイルを保持し、再実行せず調査を依頼する。プロセス停止・端末切断・電源断の後に自動復旧できるとの保証はしない。
- lockファイルは正常終了後も残るが、OSのflockはプロセス終了で解放される。ファイルを削除して排他を迂回しない。`operation.json` の途中phaseが残れば新しい反映を拒否するため、退避・ハッシュ・phaseを調査して手動復旧する。自動で未完了記録を無視したり再実行したりしない。
- **Cloudflare設定は自動で戻さない**。アプリ反映を中止/復旧した場合は、Cloudflareから今回のメール1件だけを外し、既存のInclude/Require/Excludeを維持する。会社ドメインや所有者メールを削除しない。
- アプリ側の追加を取り消す場合も、後続変更がないことを確認してから退避設定を用いて復旧する。古いバックアップで最新変更を上書きしない。
