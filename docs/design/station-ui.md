## 3. データ接続

| 対象 | 接続先 |
| --- | --- |
| 一覧・詳細・作成・編集・遷移・コメント | `GET/POST/PATCH /api/requests`、`POST /api/requests/:id/transitions`、`POST /api/requests/:id/comments` |
| 利用者・役割 | `GET /api/auth/me`、`POST /api/auth/role`（起動データの `user`） |
| 承認者名簿 | 起動データの `approvers`（`/api/approvers`） |
| 部署・道具 | 起動データの `catalog`（`listDepartments()` / `getCatalogTools()`） |
| 依頼の履歴 | 起動データの `items[].history`（`request_history`） |
| 監査（設定・DevOps・SecOps の操作） | 端末（localStorage）。画面の見本と同時に保持 |
| 監査（ログイン・役割変更・設定保存など） | `GET /api/audit-logs`（管理者）。依頼の履歴と重ならない種類だけを画面の区分に統合 |
| 開発ライン・デプロイ・脆弱性・通知・権限・ゲート | 端末（localStorage）。見本 |

- 依頼の同期は既存ブリッジの方式をそのまま使う: 端末の写しとサーバの差分を取り、
  新規 → 内容（PATCH）→ 状態（遷移）→ コメントの順で送る。失敗した依頼だけを戻す。
- 保存キーは `sf-station-v1`（依頼・見本）と `sf-station-v1-settings`（設定）。

## 4. 許容する偏差（明示）

1. **認証**: サーバのセッション（Cloudflare Access / パスワード）を使う。正本の
   「操作する人を選ぶだけ」のログインは本番の本人確認ではないため使わない。
   未認証のときはサーバが `/login` へ送る。
2. **保存**: 依頼・承認・履歴・カタログ・承認者・セッションはサーバ（PostgreSQL）。
   正本は localStorage に全データを保存するが、実装では依頼はサーバが正で、
   端末は表示用の写しを持つ（既存画面と同じ方式）。
   DevOps・SecOps の見本と、それに伴う操作ログは端末内に残る（端末を変えると別になる）。
3. **カタログ**: サーバの正本（19 部署・118 道具）を起動データで受け取って表示する。
   正本の見本カタログは 17 部署でコードが異なるため、そのままでは依頼を登録できない。
   画面の構成・文言は同じで、中身だけが実在の部署・道具になる。
4. **状態**: サーバの `release_wait`（公開承認待ち）と `cancel`（取消）を、同じ語彙・
   同じ部品（列・バッジ・パイプライン）で追加する。正本はこの 2 つを持たない。
5. **承認者の追加・変更**: サーバの利用者管理が正。設定画面は参照のみ（鍵アイコンと注記）。
6. **取り込み・初期化**: サーバ保存時は画面から実行できない（取り込むと、画面に無い依頼を
   「取消」と判定してしまうため）。運用の手順で行う。
7. **管理機能**: 正本に画面が無いため、システム設定に「利用者」「メール」タブを足した
   （運用の許容偏差）。利用者は追加・無効化・パスワード再設定（管理者のみ）、
   メールは承認依頼メールの状態・送信簿・再送・送信待ちの送信。

## 5. 実測（2026-11-11、ローカル、AUTH_MODE=password、`mirai_sf_dev`）

- 起動: 依頼 45 件、カタログ 19 部署、コンソールエラー 0。
- 役割: `requester` → `desk` / `approver` の切り替えがサーバの acting role に反映。
- 作成: 7 ステップの画面操作 → `POST /api/requests` 成功。`REQ-2026-0046`、
  承認者 ID 付き、サーバ側 `status=received`。
- 状態変更: 受付 → 内容確認中 がサーバに反映（`desk`）。
- 承認: 承認待ち → 承認済み、信号 `g` がサーバに反映（`approver`）。
