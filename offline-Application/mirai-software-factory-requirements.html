INTRODUCTION

はじめに

本書は、みらいソフトウェアファクトリー（以下「本ファクトリー」）が対象とする業務・機能・品質・統制の要件を定義する文書です。まず、何のためにこの文書があるのか、どこまでを対象とし、だれがどのように読むべきかを示します。

本書が貫く原則

作業はAI、合否は検査機（CI）、最後の決定は人。本ファクトリーは「AIに開発を丸投げする仕組み」ではなく、小さな社内道具を、安全に、速く届けるための管理された開発ラインです。以降の要件は、すべてこの原則に照らして定義します。

1.1 本書の目的

本書は、本ファクトリーを社内で構築・承認・運用するために、「何を作るか」「何をもって完了とするか」「だれが決めるか」を、実装手段に依存しない形で定めることを目的とします。具体的には、次の5点を明らかにします。

  • 対象とする業務と範囲：受付・仕様合意・実装・独立検証・承認・公開・運用改善という一連の業務のうち、本ファクトリーが担う範囲と担わない範囲。
  • 機能要件：受付アプリ、注文書、開発ライン、統制・監査、段階導入に関する43件の機能要件（FR-01-01〜FR-05-05）。
  • 品質要件：性能・可用性・セキュリティ・監査性・現場適応など12件の非機能要件（NFR-01〜NFR-12）と、データ・外部インターフェースの要件。
  • 統制と受入：権限分離、証跡、リスク対応、Phase 0〜4の受入条件、8つの測定指標。
  • 実装・検証への橋渡し：各要件から、詳細仕様書の節・テスト分類への追跡経路（第14章および付録C）。

本書は「どう作るか」の設計書ではありません。「どう作るか」は詳細仕様書（MSF-SPC-2026-001）で定義します。本書は、詳細仕様書が満たすべき要求の正本として機能します。

1.2 背景

当社には、全17部署にわたる日常業務の小さな困りごとがあります。工事写真の整理、KY記録の書きもれ確認、資機材の空き状況、請求書の仕訳候補、協力会社書類の回収状況など、一つひとつは小さくても、手作業の積み重ねが現場の時間を奪っています。従来、こうした道具の開発は、要望を集約してからまとめて発注する形が中心で、要望が現場で使われるまでに時間がかかり、途中で目的が変わったり、作ったものが使われなかったりすることがありました。

一方で、コーディングエージェント、CI、GitHubを中心とした開発基盤の進展により、「作る」ことのコストは大きく下がりました。しかし、作るコストが下がるほど、何を作るか・どこまで任せるか・何をもって合格とするか・だれが最後に決めるかという管理の側が追いつかなくなります。本ファクトリーは、この管理の側を先に設計する取り組みです。

既存の6資料（企画構想案、やさしい解説版、建設土木版、部署別道具カタログ、受付試作2種）は、この考え方を具体化した企画構想案（ドラフト）です。本書は、それらを業務・開発・監査の実務者が使える要求の形に整理し、詳細仕様書と対になる要件定義書としてまとめたものです。

既存資料の位置づけ

既存の6資料および受付試作2種は、いずれも正式決定事項ではありません。本書もドラフト（承認前）であり、目標値・初期値・工程には「（案）」を付けて提案として扱います。承認後に正式な社内標準へ移行する際は、第11章の未決事項（TBD）を解消したうえで版を更新します。

1.4 適用対象外

本ファクトリーは、社内の事務・情報系の道具を対象とします。次の領域は、本ファクトリーがAIに決めさせない領域であり、本書の要件から明確に除外します。

  • 安全・構造・品質・法令に直結する最終判断：構造計算の合否、仮設・揚重計画の決定、作業中止の判断、品質の合否判定。AIは資料集め・計算結果の整理までを担い、最終判断は資格と責任を持つ技術者が行います。
  • お金・契約・人の処遇の最終決定：契約締結、支払いの承認、金額の最終決定、採用・評価・処分。
  • 会社としての対外発表：広報・CSRとしての対外発信の可否と内容の最終決定。
  • 基幹業務システムの更改・移行：会計・人事給与などの基幹システムのリプレースは別プロジェクトとし、本ファクトリーは連携インターフェースの要件のみを扱います。
  • 既存の認証方式の変更：初期段階では既存のSSO・ID基盤をそのまま利用し、認証基盤自体の更改は対象外です（CST-08）。
  • 本番インフラの具体的な製品選定：クラウド実行基盤・データ基盤の製品は、要件ではなく選定作業として別途決定します（TBD-02）。
「動く」と「業務として正しい」は別

サンプルUIが動くことと、本番運用に耐えることは別の完了条件です。また、「検査が通った」ことは「不具合や脆弱性がない」ことの証明ではありません。対象外の判断領域にAIの出力をそのまま持ち込まないでください。

3.5 6つの実践原則

本ファクトリーを運用するうえで、技術選択より先に守るべき原則があります。これは詳細仕様書の設計にも、日々の運用にも適用されます。

原則1：最初から多数のAIを並列稼働させない

最小構成は「実装エージェント」「CI」「レビュー担当」の3つです。設計・セキュリティ等は必要に応じて追加します。役割名や別モデルを分けても誤りの独立性は保証されないため、まず仕様・自動テスト・権限制御を整備します。

原則2：実装AIが品質ゲートを自由に変更できないようにする

機能コードと追加テストは通常の作業範囲ですが、既存受入条件の削除・弱体化、CI定義・保護ルール・セキュリティ検査の無効化は別途承認を要します。重要な受入テストは実装担当と別の管理境界で保護します。

原則3：実装権限と公開権限を分離する

実装エージェントにmainへの直接書込み・本番アクセスを与えません。デプロイジョブは承認済み成果物の配備だけを行います。この分離は製品任せにせず、工場全体の設計原則とします。

原則4：エージェントの作業環境を隔離する

タスクごとに使い捨て環境を使い、ソース・テスト用データ・最小限の資格情報だけを渡します。外向き通信は必要宛先に制限し、本番DB・管理者トークン・他案件の秘密情報は渡しません。Issue・README・外部ページの文章を権限変更の命令として扱いません。

原則5：並列数より変更の衝突を管理する

1タスク＝1目的のPRとし、DBスキーマ・認証・共通部品の同時変更を制御します。API・DB契約は依存タスクより先に確定し、マージ前に最新統合状態で検証します。承認後にコミットが変わったら、検証・承認を取り直します。

原則6：AIによる自動承認と人の承認を区別する

無条件に全PRへApproveを付ける運用は避けます。自動検査は合否・根拠・未確認事項を報告し、AIレビューは指摘と見落とし得る範囲を示します。人間は業務上の妥当性と残存リスクを判断し、承認は対象コミットや公開成果物に紐付けます。

3.10 構想の到達点

本構想の到達点は、「AIが人を置き換えること」ではありません。人が本来判断すべきことに時間を使い、定型的な作業と検証の再現性を仕組みが支える状態です。

  • 受付から公開までが一本の線になる：要望・仕様・実装・検証・承認・公開が、同じIDと証跡でつながります。
  • 合格の判定が再現できる：誰が実行しても同じ手順・同じ基準で合否が出て、結果が証跡として残ります。
  • 任せる範囲と任せない範囲が説明できる：信号の色と6分類により、「なぜこの変更をAIに任せたか」を後から説明できます。
  • 小さく始めて、安全に広げられる：Phase 0〜4の終了条件で、広げてよいかをその都度判断できます。
  • 費用と品質を測りながら改善できる：8つの測定指標で、投資対効果とリスクを継続的に確認できます。
到達点の判定はPhaseの終了条件で行う

「いつまでに」ではなく「何ができたら次へ進むか」で判定します。期間を先に固定せず、各Phaseの終了条件を満たしたことをもって次段階の可否を判断します（FR-05-01）。

5.3 承認者・業務責任者の責任

承認者は、本ファクトリーの最終判断を担う最も重要な役割です。承認者の責任は、次の4点に集約されます。

  • 目的・対象・受入条件を確定する責任：要望をそのまま受け取るのではなく、何を解決し、何を作り、何を作らないかを確定します。受入条件は、検査機で合否を判定できる形にします。
  • 信号の色を決定する責任：候補色は自動判定ですが、決定は承認者が行います。赤信号の場合は「AIに決めさせない」範囲を確認し、AIの役割を材料整理までに限定します。
  • 業務としての正しさを判断する責任：テストが通るだけでなく、業務の流れ・権限・現場の使い勝手に照らして正しいかを確認します。
  • 残存リスクを理解して承認する責任：PRの「残存リスク」を確認し、公開してよいか、追加対応が必要かを判断します。判断の根拠と日時・対象コミットを記録に残します。
承認は対象コミットと公開成果物に紐付ける

承認後にコミットが変わった場合は、検証と承認を取り直します。承認の対象を曖昧にすると、監査の場で「何を承認したのか」を説明できません（FR-03-09、FR-04-03）。

13.4 重点リスクの対応

RISK-01：AI生成コードの品質・幻覚

  • AIの「成功」の説明を根拠にせず、CIの実行結果と受入条件の充足で判定します。
  • 重要な受入テストは、実装担当と別の管理境界で保護し、実装AIが弱体化できないようにします（FR-04-02）。
  • PRには残存リスクを必ず記載し、人の承認者が業務上の妥当性を確認します（FR-03-08、FR-03-09）。

RISK-04：本番データ・個人情報の漏えい

  • データ分類（第9章）に基づき、機密・秘匿情報は開発環境へ持ち込みません。
  • テストデータは作り物とし、実データのコピーを使わない運用を徹底します。
  • アクセスログと持ち出しの検知を監視し、内部監査が定期的に確認します。

RISK-08：現場定着の失敗

  • モデル現場で試用し、現場の試し係の判断を公開判断の材料にします（第6章6.6）。
  • 青信号の小さな道具から始め、現場の負担を増やさない形で広げます。
  • 利用率・現場の声を指標として観測し、使われない原因を改善します。

  • Phaseゲート：Phaseの判定時に、重点リスクの対策状況を確認します。未対策の重点リスクが残る場合は、条件付き受入または次Phaseへの持ち越しを判断します。
  • エスカレーション：影響「高」のリスクが顕在化した場合は、IT・DX責任者と承認者へ即時報告し、必要に応じて公開停止・ロールバックを判断します。
  • 記録：リスクの評価・対策・判断は記録し、監査や次年度の計画に活用します。
